## 1. Purpose & context

Kencleng is entering the development phase with an approach where
**~95% of the code is generated by an AI coding agent**, with
human-in-the-loop minimized but **not eliminated**. This is a shift in
learning focus:

- Previously: learning Go and PWA development directly, by hand.
- Now: learning the **agentic engineering workflow** — how to design
  process, spec, and verification gates so that agent-generated code
  stays correctness-critical and secure-by-design, even though a human
  isn't writing most of the lines of code.

Code quality (concurrency-safety, security) remains a mandatory
deliverable — not something traded away for automation speed. This
document is the process framework that ensures that.

## 2. Core principles

1. **Verifiability over trust** — an agent's claim that "this code is
   correct" isn't trusted at face value; it must be proven by a
   test/tool independent of the agent that wrote the code.
2. **Spec as the single source of truth** for expected behavior — not
   the agent's implicit assumptions.
3. **Risk-tiered effort** — not all code needs the same level of
   oversight. Correctness-critical areas (money, concurrency,
   auth/crypto) get stricter oversight than ordinary CRUD.
4. **Fail cheap, fail fast** — cheap gates (lint, unit tests) run
   before expensive ones (integration, security scan).
5. **Separation of authority** — the agent writing the implementation
   must not change an agreed spec or test just to make its own code
   pass.
6. **Human effort allocated to judgment, not syntax** — humans review
   things that genuinely can't be machine-verified (spec correctness,
   whether a locking strategy is adequate, etc.), not re-reading every
   diff line by line.

## 3. Document hierarchy

There are two document categories: **global** (applies to all
domains, rarely changes) and **specific** (per domain / per feature,
grows as development progresses).

### 3.1 Global documents (set up once, at the start)

| Document | Contents |
|---|---|
| `AGENTS.md` | Golden rules, Definition of Done, boundary rules for agents |
| `spec/README.md` | Spec document structure & templates (see §5) |
| `Makefile` / `scripts/verify.sh` | Single entry point for all automated gates |
| Security tool configs | `gosec`, `gitleaks`, `govulncheck`, custom lint rules |

### 3.2 Specific documents (created/grown per domain & feature)

| Level | Document | Created when | Lifespan |
|---|---|---|---|
| Domain | `spec/<domain>/invariants.md` | Once per domain, when that domain is first worked on | Stable, rarely edited |
| Domain | `spec/<domain>/threat-model.md` | Alongside the domain invariants | Stable, revised on domain-level changes |
| Feature | `spec/<domain>/features/<fitur>.md` | Per vertical slice / endpoint | New for each feature |
| Feature | Acceptance criteria + threat breakdown | Part of the feature spec above | New for each feature |

Layout is **domain-first** — `spec/<domain>/` groups all three
document types for one domain together, mirroring
`backend/internal/domain/<domain>/`. See `kencleng-repo-setup.md`
§2.1 for the full rationale. `spec/README.md` is the one file that
stays at `spec/` root (shared template, not domain-specific).

Existing documents (ERD, OpenAPI, phase docs, etc.) remain **input**
to this spec-hardening process — they aren't replaced, but derived
into a more precise/executable version.

### 3.3 Domain development order **[RESOLVED — 2026-08-04]**

```
account → notification → organisasi → campaign → donation → disbursement
```

Checked against the business-process phases (`account` = Phase 0,
`organisasi`/`campaign` = Phase 1, `campaign`/`donation` = Phase 2,
`disbursement` = Phase 3) before locking this in — domain-sequential
development tracks the phase progression closely, with one deliberate
adjustment:

- **`notification` is promoted to 2nd** (right after `account`),
  ahead of its natural dependency-graph position (last). It's
  referenced starting at Phase 1 step 2 (`organisasi_verified`) and
  is used by every domain after it — building it last would mean
  every earlier domain calls a service that doesn't exist yet.
  Promoting it costs little: `notification` is **Tier 3** (fully
  agentic, minimal review — see §4), so it's cheap infra to build
  early rather than late.
- **`campaign` spans two phases** (Phase 1: registration/curation/
  publish; Phase 2: progress/closure). This isn't a sequencing
  problem by itself, but within the `campaign` domain, features must
  still be built in phase order (curation before progress/closure) —
  don't treat "same domain" as license to build in arbitrary order.
- **Audit log** (part of `account`, built first) has write-sites
  scattered across every later domain (curation decisions, force-
  close, disbursement approval, role assignment, representative
  management). See the feature spec template in §5.3 — every feature
  spec must explicitly state whether it writes an audit log entry, so
  this isn't left to be remembered ad hoc when that domain's turn
  comes up.
- **Cross-domain invariants** (e.g. the donation ledger vs. campaign's
  `collected_amount`) are owned by whichever domain owns the
  underlying field, not by whichever domain happens to be worked on
  when the invariant is noticed. See §5.1.

## 4. Risk tiering

Every area of code is classified into one of 4 tiers. Tiering is
decided **before** coding starts, as part of the feature spec — and a
threat model can raise the tier even if the code's complexity looks
simple.

| Tier | Example areas | Mode of work |
|---|---|---|
| **0 — human-authored/paired** | Donation-processing locking strategy, disbursement state machine, encryption key handling, JWT/TOTP, money rounding | Manual, or agent-assisted with the core written/rewritten by a human |
| **1 — agent-generated + proof required** | All transaction boundaries, endpoints touching balance/status, audit log writes | Agent generates, must include property/invariant tests, mandatory human review |
| **2 — agent-generated + automated gate is enough** | Standard CRUD, DTO validation from OpenAPI, ERD-derived migrations | Agent generates, automated gates run, human spot-checks a sample |
| **3 — fully agentic, minimal review** | Component styling, non-critical UI state, seed data, documentation | Agent generates, human skims |

## 5. Spec structure per domain/feature

### 5.1 Domain invariant (`spec/<domain>/invariants.md`)

Contents: truths that must always hold regardless of which feature is
running. Written as statements that are **machine-checkable**, not
narrative.

```
Invariant: donation ledger consistency
  SUM(donations.amount WHERE status='success' AND campaign_id=X)
    = campaigns.collected_amount (for all X)
  Must remain true after: create donation, payment webhook,
  refund/cancel, concurrent donations to the same campaign.
```

**Cross-domain invariant ownership rule** **[RESOLVED — 2026-08-04]**:
when an invariant spans two domains (as above — the field
`collected_amount` belongs to `campaign`, but the concurrency-critical
write path belongs to `donation`), it is declared **once**, in the
invariants doc of whichever domain owns the underlying field or
table — `campaign/invariants.md` in this example — not duplicated.
The other domain's invariants doc references it instead of restating
it, so there's a single source of truth and no risk of the two
versions drifting apart as each domain is worked on at a different
time.

### 5.2 Domain threat model (`spec/<domain>/threat-model.md`)

- Actors & trust boundaries (simple data flow)
- STRIDE per component/endpoint
- Existing mitigations vs. knowingly accepted residual risk

### 5.3 Feature spec (`spec/<domain>/features/<fitur>.md`)

Minimum template per endpoint/feature:

```
## Endpoint: POST /donations

### Acceptance criteria
- Given ..., When ..., Then ...
- Error case: [list]

### Applicable invariants
- Reference to spec/donation/invariants.md#ledger-consistency

### Threat breakdown (derived from the domain threat model)
- Threat: double-submit race from a guest donor
  Mitigation: idempotency key required on the request
  Test: [test name]
- Threat: spoofed amount
  Mitigation: server-side recompute, ignore client-supplied total
  Test: [test name]

### Risk tier
Tier 1 — touches campaign balance

### Audit log entry?
Yes/No — if yes, which event (per
`kencleng-phase0-detail.md` §9 scope) and what's recorded.
```

**Audit log field rule** **[RESOLVED — 2026-08-04]**: every feature
spec must explicitly answer "Audit log entry?" — not left implicit.
This matters because the audit log table lives in `account` (built
first), but the actual write-sites are scattered across `organisasi`,
`campaign`, and `disbursement` features built much later — an easy
thing to forget if it's not a mandatory template field.

## 6. Workflow stages

1. **Existing documents** — ERD, OpenAPI, phase docs are the raw
   material.
2. **Harden spec** — domain invariants + feature specs are written
   (§5.1, §5.3).
3. **Threat modeling** — domain-level once, feature-level per
   endpoint (§5.2). Feeds into tiering in the next step.
4. **Risk tiering** — assign a tier per feature/endpoint (§4).
5. **Agent generates** — code + tests, per each tier's mode of work.
6. **Automated gates** — run serially, fail-fast, details in §7 & §8.
   On failure → back to step 5, the agent revises, without waiting on
   a human.
7. **Human checkpoint** — only for Tier 0-1 (plus spot-checks for
   Tier 2). Scope details in §9.
8. **Merge & deliver.**

## 7. Automated testing — layers & execution order

Run **serially between stages** (cheap → expensive, fail-fast),
**in parallel within a stage** (e.g. unit tests across packages).
Retries restart from the earliest stage every time the agent changes
code — not just resuming from the failed stage — because a fix in one
place can break another.

| Order | Stage | Concrete example | Tool |
|---|---|---|---|
| 1 | Static/lint | ban `float64` in the money package, ban `fmt.Sprintf` into queries | `staticcheck`, custom lint |
| 2 | Unit tests | fee calc, rounding, state-transition validity | `go test` |
| 3 | Concurrency | N goroutines donating concurrently, no lost update | `go test -race` + stress harness |
| 4 | Property-based | invariant holds for N random inputs | `pgregory.net/rapid` / `gopter` |
| 5 | Contract test | response matches the `openapi.yaml` schema | `kin-openapi` validator |
| 6 | Security — layer A (deterministic) | see §8.1 | `gosec`, `gitleaks`, `govulncheck` |
| 7 | Integration | full flow against a real Postgres | `testcontainers-go` |
| 8 | Security — layer B (LLM review) | see §8.2 | separate agent, fresh context |

All stages are wrapped by one entry point (`make verify`) that
outputs an exit code + structured (JSON) report — so the agent can
parse failures mechanically instead of guessing from free-form logs.

## 8. Security testing — two layers

### 8.1 Layer A — deterministic tools (mandatory, cheap, run first)

| Issue | Approach |
|---|---|
| SQL injection | `goqu` exclusively (parameterized) + `gosec` G201/G202 + lint banning raw strings into queries |
| XSS / client-side injection | React auto-escaping; ban `dangerouslySetInnerHTML` without review; sanitize narrative Markdown (`rehype-sanitize`/DOMPurify) |
| CSRF | state-changing endpoints only accept JSON + a custom header (consistent with same-origin + `SameSite=Strict`) |
| Secret leaks | `gitleaks` on every commit/PR + pre-commit hook |
| Improper error messages | test: trigger an internal error, assert the response doesn't leak stack traces/paths/raw SQL errors |
| Log/audit repudiation | test: the application's DB role fails to `UPDATE`/`DELETE` the audit log table (DB-level privilege) |
| Sensitive data exposure | test: PII columns in the DB are ciphertext; response schemas never expose raw fields |
| Dependency vulnerabilities | `govulncheck`, `osv-scanner` |
| Security headers | test that CSP, `X-Content-Type-Options`, etc. are present on responses |
| Rate-limit bypass | test that 429 appears after the threshold |

### 8.2 Layer B — LLM security review agent (after layer A passes)

- Catches logic-level vulnerabilities tools can't: an authz check
  missed on an edge case, IDOR, business-rule bypass via an unusual
  call sequence.
- Context provided: the diff + the relevant feature's threat model
  (not the whole codebase).
- Explicitly adversarial prompt ("find a way to make this fail
  safely," not "confirm this is safe").
- Output must be structured: severity, location, category (mapped to
  OWASP ASVS/Top 10).
- **Fresh context required** — not the same agent/session that wrote
  the code.
- Periodic calibration: occasionally seed deliberately vulnerable
  code to confirm this agent actually catches it, rather than always
  saying things are safe.

## 9. Agent honesty about risk

Because the agent generating code and the agent self-reporting its
quality both have a built-in incentive toward "looks done":

- **Risk note required**, fixed format, per PR: assumptions made,
  edge cases intentionally/not-yet handled, concurrency assumptions,
  what wasn't tested and why.
- **Claims must be grounded in a concrete test** — "edge case X is
  handled" without naming the test that proves it is treated as
  invalid.
- **Independent adversarial pass** — a second session/agent, fresh
  context, asked to find flaws without seeing the original risk note.
  The gap between its findings and the original risk note shows what
  was missed/omitted.
- **Explicit framing in the prompt**: reporting a risk = success; a
  risk discovered later that wasn't reported = failure.

## 10. Human checkpoint — required scope

Not a syntax review (already gated automatically). Focus on what
genuinely needs human judgment:

1. Correctness of the spec itself — do the invariants/threat model
   actually represent the correct business rule.
2. Locking/transaction reasoning — is the strategy adequate for all
   plausible concurrent scenarios, not just what the race detector
   happened to catch in one run.
3. Authz negative-path — read it directly, don't just trust a green
   test.
4. Agent's risk note — decide whether the flagged risk is acceptable
   for this tier/phase.
5. Gates aren't "gamed" — assertions actually test something,
   thresholds haven't been quietly lowered.
6. Diff shape — a "small" feature that suddenly touches dozens of
   unrelated files is a red flag even if all gates are green.

## 11. Agent constraints (fencing)

- **Scope fencing** — one vertical slice/endpoint per session.
- **Authority separation** — the implementing agent must not edit
  spec or test files that have already been agreed on.
- **Environment fencing** — work happens in local docker-compose,
  dummy credentials, no external access beyond a whitelist.
- **Git/PR fencing** — one branch per slice, small PRs, gates must
  pass before merge, commits reference the spec file being fulfilled.
- **File-path fencing for Tier 0** — areas like
  `internal/domain/donation/ledger.go` or
  `internal/platform/crypto/` are marked "no-agent-write" in
  `AGENTS.md`.

## 12. Per-domain execution checklist — backend track **[RESOLVED — 2026-08-04]**

Concretizes §6's abstract stages into an actual sequence, worked out
for `account` as the first domain. This is the **backend** track
specifically — see §14 for the analogous frontend track, and §15 for
how the two tracks fit together at the domain level (sequencing,
Finalize, Delivery).

**Once per domain:**
1. Check reference material (ERD, relevant OpenAPI tag, phase-detail
   doc, tech-stack docs)
2. Confirm agent guidelines/skills are ready (`AGENTS.md`,
   `spec/README.md` template, `Makefile`/`verify.sh`)
3. Write `spec/<domain>/invariants.md`
4. Write `spec/<domain>/threat-model.md`
5. Enumerate the task list (per endpoint/feature), assign a Tier
   (§4) and delivery KPI/metrics to each
6. Group tasks by whether they can run in parallel or must be
   serial (see parallelization note below)

**Loop, per task:**
7. Analyze (Explore + Plan) → write `spec/<domain>/features/<fitur>.md`
   (acceptance criteria, threat breakdown, tier, audit-log field —
   §5.3)
8. Build (agent generates code + tests, per the tier's mode of work)
9. Gates, serial, fail-fast (§7): lint → unit → concurrency →
   property-based → contract → functional/API → security layer A →
   integration → security layer B → performance (only where
   concurrency load is a genuine concern, not every endpoint)
10. On any gate failure → back to step 8, agent revises
11. Agent writes the risk note (§9)
12. Human checkpoint (§10) — mandatory for Tier 0-1, spot-check for
    Tier 2
13. Merge & deliver

**Parallelization**: steps 1-6 are serial (one pass per domain).
Within the task loop, **different tasks can run in parallel** if they
don't touch overlapping files, tables, or migration numbers (e.g.
"Registrasi" and "Role Assignment" are independent enough to
parallelize; "Login & Session" and "Forgot Password" share the same
`AuthIdentity`/token tables and are safer run serially). Gates
*within* one task (step 9) are always serial — the cheap-to-expensive
ordering is deliberate and isn't parallelizable. Human checkpoint is
always serial by nature.

**Known risk with parallel task execution**: `golang-migrate` uses
sequential file numbering — two agent sessions generating migrations
concurrently can collide. Needs a concrete mitigation (e.g.
pre-assigned number ranges per task) before parallel execution is
actually used, not just assumed safe.

## 13. Work allocation — Assisted / Manual / Full Agent **[RESOLVED — 2026-08-04]**

Every step in §12 falls into exactly one of three buckets:

### 13.1 Assisted (Claude chat — spec/planning only, no repo access)

Steps 1-6, and the **Plan** half of step 7 (writing the feature spec
itself). This matches the project's standing rule that Claude's role
here is documentation and planning, not code.

**Important boundary**: step 7 is actually two sub-parts — *Explore*
(reading the existing codebase) and *Plan* (writing the spec).
*Explore* cannot happen in this chat — there's no repo access here,
only project docs. Once a domain has real code in it (e.g. `Login` is
built and `Forgot Password` needs to reuse its tables), the *Explore*
half must happen in the coding agent (which has repo access), and only
the resulting *Plan* comes back here for spec-writing. Early tasks in
a fresh domain (nothing built yet) have a trivial/doc-only Explore
step, so this boundary matters more as the domain fills in.

### 13.2 Manual (human-only — Anhar)

- Human checkpoint (step 12) — always, mandatory for Tier 0-1
- **Reading DB query plans (`EXPLAIN ANALYZE`) for Tier 0 queries**
  (ledger writes, refresh-token rotation) — a plan can look correct
  and still be wrong under concurrent load; this is exactly the kind
  of thing §2's principle 6 says can't be machine-verified
- Deciding whether an agent-flagged risk is acceptable for the
  tier/phase
- Writing or rewriting the core logic of Tier 0 areas (money
  rounding, JWT/TOTP, refresh-token reuse detection, disbursement
  state machine) — per the Tier 0 definition in §4 itself
- **Applying an index change to a Tier 0 table** (ledger/token
  tables) — an index can change row-lock scope (`FOR UPDATE`), so
  even if the index is agent-*proposed*, applying it to a
  money-critical table is a manual action
- **Applying an index change to any table** (not just Tier 0)
  **[RESOLVED — 2026-08-04]**: agents may *propose* indexes (based on
  observed query patterns) for any table, but *applying* the change is
  always a manual, human-triggered action — even for ordinary CRUD
  tables. Chosen over letting the agent auto-apply for non-Tier-0
  tables, trading a little friction for an explicit human trigger
  point on every schema-affecting change, not just the money-critical
  ones.

### 13.3 Full AI Agent (coding agent, autonomous)

- Build (code + test generation) — step 8
- Unit tests, concurrency tests (race detector + stress harness),
  property-based tests, contract tests, functional/API tests
- Security layer A (deterministic tools: `gosec`, `gitleaks`,
  `govulncheck`) — fully automatable
- Integration tests (`testcontainers-go`)
- Security layer B (LLM adversarial review) — full agent, but
  **must be a separate agent/fresh context** from the one that wrote
  the code (§8.2) — not the same agent doing everything end-to-end
- Performance test + profiling, where concurrency load is a genuine
  concern for that specific endpoint (not blanket-applied to every
  endpoint — consistent with the lowest-complexity principle)
- DB index *recommendation* (proposal only — see §13.2 for the apply
  rule)
- Risk note authoring (step 11) — agent writes it, human evaluates it
  (§13.2)

## 14. Per-domain execution checklist — frontend track **[RESOLVED — 2026-08-04]**

Analogous to §12, but for the PWA frontend. Backend-specific tooling
(`golang-migrate`, `testcontainers-go`, `gosec`) doesn't apply here —
frontend has its own gate order, not previously specified.

**Once per domain:** same steps 1-6 as §12 aren't repeated — domain
invariants/threat model are domain-level artifacts shared by both
tracks, not duplicated per track. Frontend adds one thing to check at
this stage: confirm the relevant `openapi.yaml` schemas for the
domain are stable (they are — spec phase is closed), since frontend
work is contract-driven and builds against mocked responses, not a
live backend.

**Loop, per task (per page/component/flow, not necessarily 1:1 with
backend endpoints):**
1. Analyze (Explore + Plan) → same feature spec in
   `spec/<domain>/features/<fitur>.md` already written for the backend track
   covers this — frontend doesn't get a separate spec doc, it
   implements against the same acceptance criteria plus
   `kencleng-ux-page-map.md` / wireframes / design guidelines
2. Build (agent generates component + page code, using
   `openapi-typescript`-generated types from `api/openapi.yaml` as
   the contract)
3. Gates, serial, fail-fast:
   lint (ESLint) → unit/component test (Vitest + React Testing
   Library, API calls mocked via MSW using the OpenAPI schema) →
   contract check (generated types match the mock fixtures actually
   used in tests — catches drift between `openapi.yaml` and what the
   component assumes) → accessibility check (contrast/focus rules per
   `kencleng-design-guidelines.md`) → *(E2E: explicitly out of scope
   for v1, per the frontend tech-stack doc)*
4. On any gate failure → back to step 2, agent revises
5. Agent writes the risk note (§9) — for frontend this is mainly
   "what did I assume about an error/empty/loading state that isn't
   nailed down in the spec yet" (see §15 — Finalize is where these
   get resolved for real)
6. Human checkpoint — same Tier-based rule as §10, but note frontend
   work is rarely Tier 0 itself (Tier 0 is about server-side
   correctness-critical logic); a frontend task's tier is inherited
   from the backend feature it's presenting, mainly to flag "does
   this screen handle a Tier 0 feature's error states carefully"
   rather than "is this component doing money math" (it shouldn't be)
7. Merge

Because frontend tests are mocked against the contract (MSW), this
track doesn't require a live backend to develop or test against —
which is exactly what makes the parallel-track option in §15
possible for domains where it's worth the added coordination.

## 15. Domain-level sequencing: backend track, frontend track, Finalize, Delivery **[RESOLVED — 2026-08-04]**

Two tracks (§12, §14) plus two domain-level closing stages, per
domain:

```
[docs: §12 steps 1-6, once]
        │
        ▼
[backend track: §12 loop, all backend tasks for the domain]
        │
        ▼
[frontend track: §14 loop, all frontend tasks for the domain]
        │
        ▼
[Finalize]
        │
        ▼
[Delivery]
```

**Backend-then-frontend sequencing is a per-domain decision, not a
fixed rule** — re-evaluated at the start of each domain (§12 step 1-6
stage), not assumed. It's decided in favor of contract-driven
parallel tracks specifically where the added coordination overhead is
worth it (e.g. a large or time-pressured domain). For `account` — the
first domain, where the priority is learning to run the agentic
workflow itself cleanly before adding coordination complexity —
**sequential is chosen: backend track runs to completion first, then
frontend track starts.** This also keeps backend/frontend learning
genuinely separate for this first domain, per the project's own
working principle, rather than context-switching between them
per-feature.

**Finalize** (once per domain, after both tracks are done):
- Full stack up via `docker-compose` (backend + frontend + Caddy +
  Postgres + MinIO) — real integration, not mocks
- Manual smoke test of every feature in the domain, end-to-end
- Resolve empty/loading/error states concretely per page (this was a
  deliberate, documented deferral to implementation time — see
  `kencleng-roadmap-next-steps.md` Open Item #13 — this is where that
  deferral gets closed out)
- Check conformance against wireframes and `kencleng-design-
  guidelines.md`
- Manual (§13.2) — this stage is inherently about judging real,
  connected behavior, not something automated gates can substitute for

**Delivery** (once per domain, after Finalize passes):
- Merge to main
- Update the development-phase tracker (a new tracker — the existing
  `kencleng-roadmap-next-steps.md` only tracks the now-closed
  documentation/spec phase; a development-phase equivalent doesn't
  exist yet and is itself an open item — see §16)
