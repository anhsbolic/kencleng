## What & why

This plan reconciles the per-Campaign individual Donation limit and cumulative funding capacity across Product/MVP, Campaign and Donation specifications, and authored API sources. It gives backend and frontend delivery planning an accepted, consistent contract while preserving full settlement for accepted pending Donations and keeping capacity distinct from the existing funding threshold.

## Interface Contract

| Concern | Contract |
|---|---|
| Operations | `POST /organizations/{organizationId}/campaigns`, `PATCH /campaigns/{campaignId}`, public `GET /campaigns/{campaignId}`, and `POST /campaigns/{campaignId}/donations`. |
| Authentication / authority | Existing operation authority remains source-defined; Campaign owns cap configuration/lifecycle, Donation owns admission and full-value settlement. Concrete API source changes still require applicable review and owning API acceptance. |
| Trigger / caller | Campaign owner/staff configure the cap while draft; public detail discloses it before donation entry; Donation POST independently rechecks cap and eligibility. |

**Request / input**

| Field / input | Meaning / requirement |
|---|---|
| `max_donation_amount` | Optional on create and PATCH. If supplied, it is a closed object with required `amount` (major-unit decimal string) and `currency_code` (`IDR`). Create omission defaults to Rp1,000,000,000; PATCH omission preserves the current value. |
| `amount` | Whole-IDR Donation amount; must meet the configured individual cap and fit remaining eligible Campaign capacity. |

The following is a representative field fragment, not a complete request payload:

```json
{
  "max_donation_amount": {
    "amount": "1000000000",
    "currency_code": "IDR"
  }
}
```

**Response / output**

| Field / output | Meaning |
|---|---|
| `max_donation_amount` | Required on Campaign and public-detail responses as a closed object with both required members, including explicit currency when public Funding is unavailable. |
| `closed_reason` | Campaign adds the distinct internal reason `funding_capacity_reached`; it remains distinct from `max_amount_reached`. |
| Public closure/action | Slice-2 closed detail remains non-public/404 per current contract; Slice-3 handoff owns identity retention, action removal, and non-final Funding while accepted pending Donations remain. |

**Error behavior:** Individual over-cap and eligible capacity no-fit return the shared generic `422 ValidationError` on `amount`. Capacity no-fit means the Campaign remains eligible, the requested amount cannot fit, and a smaller valid amount can; the response does not disclose capacity. Closed/ineligible remains `409`, and existing idempotent retry behavior remains. Backend predicates stay distinct.

## Key decisions

| Decision | Why / consequence |
|---|---|
| Per-Campaign whole-IDR maximum from Rp5,000 to Rp1,000,000,000; default Rp1,000,000,000; Owner/Staff draft configuration frozen on publication. | Sets the individual admission promise and prevents published terms from changing. |
| Create omission defaults; PATCH omission preserves existing value; existing rows receive the default direction. | Prevents unrelated updates from resetting a configured cap and defines compatibility direction. |
| Public detail discloses the cap before entry, while POST independently rechecks it. | GET is an informational snapshot, not admission authority. |
| Capacity counts settled plus accepted pending amounts; close when exhausted and never reopen after pending failure. | Protects full settlement and stable closure semantics. |
| `funding_capacity_reached` is distinct from threshold closure; Slice-3 public result behavior remains a later applicability handoff. | Preserves existing threshold meaning and prevents this slice from silently changing closed-detail visibility. |
| Use a closed `{amount, currency_code}` object; eligible capacity no-fit uses shared generic 422 on `amount`. | Keeps amount and currency explicit and avoids public capacity disclosure while retaining distinct server predicates. |
