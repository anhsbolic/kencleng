## Interface Contract

The Techplan requires guest submission and guest status lookup, but deliberately leaves operation paths and finalized request/response shapes to authored split OpenAPI reconciliation. No endpoint, payload example, or unfixed field is asserted here.

| Concern | Contract |
|---|---|
| Endpoint / event / interface | Guest donation submission and guest donation status lookup; exact paths and shapes remain for authored API reconciliation. |
| Authentication / authority | Guest status uses the selected temporary status credential and returns status-only information. The frontend hands off the fragment credential and cleans the URL; the verifier is one-way HMAC. |
| Trigger / caller | A guest initiates submission; the guest later revisits status through the frontend handoff. No client-callable settlement interface is allowed. |

**Request / input**

| Field / input | Meaning / requirement |
|---|---|
| Donation amount | Whole-IDR Rupiah input, minimum Rp5.000 and Rp1 increments; API/wire monetary values use major-unit decimal strings paired with explicit currency codes. Exact-decimal calculation and persistence; no float/float64. |
| Submission retry identity | Same key and same payload on ambiguous retry returns the original Donation; same key with changed payload is rejected. A new key represents a new Donation only after deliberate donor action. |
| Guest status credential | Human-selected fragment URL flow, frontend handoff and URL cleanup, one-way HMAC verifier, hard 24-hour validity from issuance without extension. Remaining carrier/header expression must follow that flow. |

No representative request example is included because the source Techplan has not fixed the operation or payload shape.

**Response / output**

| Field / output | Meaning |
|---|---|
| Donation state | Persisted `pending` followed only by backend-simulator-owned terminal `success` or `failed`; pending does not auto-resubmit. |
| Status lookup projection | Status-only access. Successful settlement and the full funding increment are one atomic business outcome, counted exactly once. |
| Monetary values | Major-unit decimal strings with explicit currency code; exact value preserved end-to-end. |

No representative response example is included because the source Techplan has not fixed response fields.

**Error behavior:** Missing, wrong, or expired status credential and absent Donation share one public `404` with identical Problem Details body, headers, and cache behavior, including `Cache-Control: private, no-store`. Exact Problem Details coordinates and authored cache expression remain API reconciliation. Empirical body/header/cache and timing parity are downstream evidence, not established by this plan. Same-key/different-payload submission is rejected; exact response encoding remains to be specified in OpenAPI.

## Key decisions

| Decision | Why / consequence |
|---|---|
| Guest donation without an Account is in Slice 2; backend simulator owns persisted `pending`/`success`/`failed`. | Keeps the flow within approved MVP scope and prevents client-selected or client-forged settlement. |
| IDR input is whole Rupiah, minimum Rp5.000, while wire money uses major-unit decimal strings plus explicit currency; calculations/storage preserve exact decimals. | Carries approved Slice 2 input and project-wide monetary standard without inventing unsupported currency or precision rules. |
| Only QRIS is an active, clearly labeled sandbox simulation among the four displayed method labels. | Prevents inactive methods from implying real payment capability. |
| Same-key ambiguous retries return the original donation; changed payload with the same key is rejected. | Prevents accidental duplicate intent while keeping submission retry distinct from settlement replay. |
| Fragment status URL with frontend handoff/URL cleanup, one-way HMAC verifier, 24-hour hard expiry, and status-only projection; missing/wrong/expired credential and absent Donation use a uniform public `404`. | Restores the already-selected O4/O5 directions into the contract. This resolves fidelity findings without selecting new controls or accepting risk. |
| `max_amount` is a threshold; eligibility is ordered against Campaign close, accepted Donations settle in full, and successful settlement/funding update commit exactly once. | Preserves the approved Campaign/Donation ordering, stable close reason, and possible threshold overshoot without adding Slice 3 lifecycle. |
| Verified opted-in email remains eligible until its terminal notice is fulfilled; Delivery must make terminalization bounded and recoverable. | Implements the settled O11 direction while leaving its operational bounds, architecture, and risk acceptance open. |
| The completed O7 source-first simulation labels and optional-email disclosure remain the selected Design wording. | Carries settled copy into future contract/UI work; rendered acceptance remains later. |
| Historical submit/status operations may be replaced only within this repository/current Slice 2 scope. | O8 confirmation is bounded; it does not assert that no possible external consumer exists. |

## Material risks / trade-offs

| Risk / trade-off | Exposure / mitigation | Status |
|---|---|---|
| Money precision or accidental float use can alter monetary meaning. | Exact-decimal/no-float contract is settled; unsupported ranges, currency fractions, and derived rounding remain deferred until needed and owner-resolved. | Mitigated at plan level; runtime proof remains later. |
| Guest email or bearer status credentials can expose PII/access, or terminal notice can be delayed/lost. | Selected verification/status directions and O11 obligation are explicit; controls, bounded/recoverable delivery design, lifecycle evidence, abuse prevention, and risk acceptance remain with owners and later gates. | Open follow-up; no residual risk accepted. |
| Public lookup outcomes may differ through response or timing, enabling enumeration. | Uniform `404`, identical body/header/cache contract, and `private, no-store` are required; Testing must establish runtime parity and abuse evidence. | Contract direction settled; runtime proof open. |
| Concurrent submission, close, or settlement can diverge from funding truth. | Atomic eligibility/order and exact-once settlement/funding behavior are required; mechanism is not prescribed and specialized runtime evidence remains necessary. | Contract direction settled; implementation and proof open. |
| Simulator or inactive-method presentation may imply real payment or an SLA. | QRIS-only sandbox, unavailable labels, selected status copy, and no timing promise are carried forward. | Mitigated by plan requirements; rendered acceptance and delivery detail remain later. |
