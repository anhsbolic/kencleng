## What & why

Techplan ini merencanakan alur donasi publik oleh guest dari Campaign yang tersedia, melalui pengiriman QRIS sandbox, hingga pemeriksaan status yang jujur. Tujuannya adalah membuat batas donasi dan mata uang jelas sebelum donor mengisi nominal, memakai kontrak Campaign/Donation yang telah diterima, dan menjaga perbedaan antara hasil simulasi dengan settlement nyata.

## Scope

**Included**
- Perubahan frontend untuk detail Campaign publik, entry ke formulir donasi guest, submission, hasil/status, dan pemulihan error sesuai kontrak saat ini.
- Pengungkapan `max_donation_amount` beserta IDR sebelum input nominal; disclosure tetap membawa mata uang eksplisit ketika Funding tidak tersedia.
- QRIS sebagai satu-satunya metode interaktif untuk simulasi; GoPay, ShopeePay, dan bank transfer tetap tampak tetapi unavailable dan non-interaktif.
- Field guest opsional, idempotency yang mempertahankan intent, status credential handoff yang aman, serta MSW dan pemeriksaan frontend yang mengikuti kontrak.

**Explicitly not included this round**
- Backend DTO/wire response, cap/capacity enforcement, eligibility, idempotency persistence, simulator, settlement, credential controls, verifikasi/pengiriman email, atau database.
- Perubahan Product, spec, API, generated types, fixture sumber bersama, tracker, atau Work Unit lain.
- Detail Campaign tertutup untuk publik, perilaku Slice 3, akun/riwayat donor, metode pembayaran selain QRIS, atau payment rail nyata.
- Klaim runtime/security acceptance, integrasi backend nyata, rendered acceptance, penerimaan residual risk, atau penyelesaian milestone berdasarkan mock.

## Architecture / Plan

Rencana memperluas komposisi detail Campaign untuk menampilkan cap dan IDR dari projection yang diterima, lalu menggunakan `donation_action` sebagai satu-satunya affordance masuk. Route guest memakai Campaign ID, form menggunakan validasi UX lokal tanpa mengarang batas kapasitas, dan adapter mengirim request bertipe dengan idempotency key stabil. UI membedakan validasi amount `422`, kondisi Campaign `409`, dan kegagalan transport; status yang tampil tetap bersumber dari backend. Route status mengambil credential dari URL fragment, membersihkan URL yang terlihat, mengirim credential melalui header yang ditetapkan, lalu hanya menampilkan status. MSW memotong di network boundary untuk membuktikan perilaku frontend, bukan backend.

**Components touched**

| Component | Purpose / change |
|---|---|
| Campaign detail frontend | Menampilkan cap/mata uang dan mempertahankan perilaku action available/unavailable. |
| Guest Donation routes and form | Menangani input, optional fields, QRIS sandbox submission, hasil, dan status. |
| Frontend API adapters and state | Mengirim request/status sesuai generated contract dan menjaga intent/recovery. |
| MSW handlers, fixtures, and frontend checks | Memodelkan kontrak jaringan dan memverifikasi observasi UI yang direncanakan. |

**Not touched / blast-radius boundary:** `backend/`, authored `api/`, Product/spec, generated API types, serta area Tier-0 terlindungi tidak diubah oleh Techplan ini. Tidak ada perubahan data persisten yang direncanakan. Exact Campaign response DTO/wire assertion tetap milik WU-S2-003.

## Interface Contract

Techplan frontend ini mengonsumsi kontrak berikut; tidak mengubah atau menerima ulang source contract tersebut. Backend tetap otoritatif untuk eligibility, cap/capacity, idempotency, status, dan kredensial.

| Concern | Contract |
|---|---|
| Campaign detail | `GET /campaigns/{campaignId}` menyediakan `PublicCampaignDetail` termasuk `max_donation_amount` berisi amount dan `currency_code: IDR`, Funding projection, serta union `donation_action`. Projection adalah snapshot, bukan otorisasi. |
| Guest submission | `POST /campaigns/{campaignId}/donations` menerima `Idempotency-Key` dan request QRIS. Eligible capacity no-fit memakai generic `422 ValidationError` pada `amount`; Campaign closed/ineligible tetap `409`. |
| Status | `GET /donations/{donationId}/status` menerima credential via `X-Donation-Status-Credential`, menghasilkan status saja, dan memakai failure publik generik untuk credential/kondisi yang tidak valid atau tidak tersedia. |
| Caller / authority | Donor guest memulai dari action yang diproyeksikan; server memeriksa ulang eligibility dan aturan admission. Frontend tidak menghitung sisa kapasitas atau menyimpulkan alasan tersembunyi. |

**Error behavior:** Pertahankan perbedaan feedback amount `422` dan closed/ineligible `409`; jangan tampilkan capacity/close reason tersembunyi. Status missing/wrong/expired/absent memakai kegagalan publik generik. Tampilkan error aman dan pertahankan input bila pemulihan didukung kontrak.

## Key decisions

| Decision | Why / consequence |
|---|---|
| `donation_action` menjadi sumber entry; POST tetap otoritatif. | GET hanya snapshot dan tidak boleh berubah menjadi keputusan authorization di client. |
| Cap individual Campaign dan IDR tampil sebelum donor memasukkan nominal, termasuk saat Funding projection unavailable. | Menjaga disclosure finansial jelas; cap bukan `max_amount` dan bukan kapasitas tersisa. |
| Eligible no-fit menggunakan generic `422` pada `amount`, sementara closed/ineligible memakai `409`. | Mempertahankan predicate server yang berbeda tanpa mengungkap kapasitas. |
| Submission memakai intent/idempotency yang stabil; hanya QRIS yang aktif dan mengirim request. | Menekan duplikasi dan memastikan metode display-only tidak dianggap metode pembayaran yang didukung. |
| Status credential hanya dipindahkan dari fragment ke request header lalu URL dibersihkan; status view tidak menyimpan token. | Mengurangi paparan credential di URL terlihat dan menjaga status access sesuai kontrak. |
| MSW berada di batas jaringan dan fixture mengikuti generated contract. | Bukti mock/UI hanya membuktikan frontend; bukan integrasi, keamanan server, atau settlement. |

## Material risks / trade-offs

| Risk / trade-off | Exposure / mitigation | Status |
|---|---|---|
| Cap tidak tampil, mata uang hilang, atau snapshot dianggap jaminan admission. | Tampilkan cap IDR sebelum input termasuk Funding-unavailable; POST tetap validasi otoritatif dan absence kontrak ditangani sebagai kegagalan aman. | Mitigasi direncanakan; rendered acceptance masih terbuka |
| Retry atau aktivasi berulang membuat intent donasi ganda atau payload/key tidak konsisten. | Rencana mempertahankan key+payload untuk ambiguous retry, menekan aktivasi ganda, dan membuat key baru hanya untuk intent baru yang disengaja setelah known failure. | Verifikasi implementasi belum dilakukan |
| Credential status bocor atau status dapat dienumerasi. | Fragment handoff, URL cleanup, header, status-only response dan generic failure; keamanan credential/infrastruktur serta anti-enumeration memerlukan bukti backend/runtime terpisah. | Open downstream |
| Email opt-in memberi kesan ownership terverifikasi atau notifikasi pasti terkirim. | Copy/helper dan request opt-in mengikuti accepted direction; frontend tidak mengklaim verifikasi/pengiriman tanpa bukti. | Kontrol verifikasi/delivery masih open |
| MSW atau tampilan terminal dianggap bukti settlement nyata. | Gunakan wording simulasi yang ditetapkan dan laporkan bukti sebagai frontend mock saja. | Batas dinyatakan; integrasi/runtime masih terbuka |
