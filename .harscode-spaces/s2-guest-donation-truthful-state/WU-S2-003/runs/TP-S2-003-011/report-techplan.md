## What & why

This plan delivers the backend guest Donation path for Slice 2 with persisted, truthful sandbox outcomes and exact Campaign Funding effects. It joins guest submission and status access to Campaign-owned eligibility, capacity, and close coordination so clients see consistent results without implying real payment settlement.

## Scope

**Included**
- Guest Donation submit, same-intent retry, persisted pending/success/failed simulator states, guest status access, and optional verified terminal email.
- Campaign-owned D1 admission/close/settlement coordination, full accepted-pending capacity reservation, and exact-once full Funding contribution.
- Accepted public Campaign cap projection and advisory `donation_action`, with POST independently enforcing current eligibility and capacity.
- Campaign draft create and PATCH for the accepted cap configuration, including the full accepted request, authorization, validation, default/preserve, and publication-freeze behavior.
- Minimum persisted representative membership and Organization eligibility facts needed by those handlers, subject to the scoped Open Item 7 gate.
- Additive migration design and focused implementation evidence; migration/index application remains Human-triggered.

**Explicitly not included this round**
- Frontend, Product/spec/API authority changes, or edits to the accepted source snapshot and reconciled counterparts.
- Accounts, donor history/list/claim, guest-email reveal, Campaign-wide notification, real payment rails, or real-world settlement claims.
- Full Slice 3 lifecycle, deadline scheduler, administrative force-close, public closed-detail activation, Campaign DELETE, curation, publish/schedule, unpublish, media-write, or representative-management/self-service UI.
- Unowned Organization-truth mutation paths, inferred membership from JWT claims, or an unapproved operator role.
- Writes to protected ledger/transaction locking, crypto/auth, or disbursement state-machine code absent their required Human authorization and pairing.

## Architecture / Plan

Campaign owns eligibility, lifecycle, authoritative Funding, and the first winning close reason. Donation owns request identity, persisted state transition, simulator result, and contribution. A Campaign-owned coordinator serializes admission, close, reservation, and settlement. Existing same-intent retries resolve before new-intent eligibility rejection; new requests require authoritative settled Funding and fail closed if it is unavailable. Accepted pending amounts reserve capacity, successful terminal state and full Funding commit atomically, and failed/pending amounts do not count as collected Funding. Public availability remains informational.

Campaign draft handlers use accepted Owner/Staff membership scoped to the Organization and fresh Organization eligibility facts. Their source updates and affected handlers remain gated until Open Item 7 assigns authority and governance. Donation/D1 schema work remains behind a fresh positive migration-design Review. No diagram is needed for this bounded prose flow.

## Interface Contract

The candidate preserves accepted contracts and identifies backend implementation work; WU-S2-007's accepted API/counterpart reconciliation is not backend runtime evidence.

| Concern | Contract |
|---|---|
| Donation submission | `POST /campaigns/{campaignId}/donations`; guest request, accepted idempotency header, pending response, QRIS simulation. |
| Guest status | `GET /donations/{donationId}/status`; optional credential header, status-only response, fragment-based credential handoff. |
| Public Campaign detail | Required closed `max_donation_amount` object with decimal-string amount and `currency_code: IDR`, including Funding-unavailable state. |
| Campaign availability | `donation_action` is informational; submission independently rechecks eligibility and capacity. |
| Campaign draft writes | `POST /organizations/{organizationId}/campaigns` and `PATCH /campaigns/{campaignId}` with accepted representative authorization, validation, draft-only updates, and response semantics. |
| Authentication / authority | Guest for Donation submit/status; accepted authenticated Owner/Staff membership for Campaign writes. Organization fact setting/update authority remains gated by Open Item 7. |

**Request / input**

Donation accepts the contract-defined amount and fields. Retry equivalence includes Campaign route ID and every accepted field after defaults, including optional PII; comparison uses a keyed HMAC fingerprint. Campaign create/PATCH use the existing accepted `CampaignCreateRequest` / `CampaignUpdateRequest` contracts. This report does not add request fields.

**Response / output**

Submission persists `pending`. Over-cap or eligible capacity no-fit returns generic shared `422` on `amount`; closed/ineligible and changed-payload key reuse retain `409`. If authoritative settled Funding is unavailable, no Donation is admitted and the response is generic `503 Problem` without internal reason or `Retry-After`. Status success is status-only; absent Donation and missing, wrong, or expired credential have uniform `404` behavior. Both status `200` and `404` use `private, no-store`.

**Error behavior:** Preserve the accepted `401`/`403`/`409`/`422` Campaign write contract, generic Donation validation/ineligibility errors, and fail-closed Funding-unavailable behavior. Do not disclose remaining capacity or close reason.

## Key decisions

| Decision | Why / consequence |
|---|---|
| Campaign owns lifecycle and first close reason; Campaign-first `READ COMMITTED` row lock coordinates D1 before Donation rows. | Keeps authorization and close ordering with Campaign. Protected implementation remains separately Human-authorized and paired. |
| Donation values use exact whole Rupiah Rp5,000–Rp1,000,000,000; Campaign cap defaults to Rp1,000,000,000, while total Funding has a separate finite ceiling and pending reservation. | Preserves accepted amount/capacity boundaries without adopting a project-wide database scale. |
| Existing matching retry resolves before new-intent closed rejection; changed payload conflicts. | Makes retry return the original intent after closure while preventing key reuse for different intent. |
| Status uses fragment handoff/cleanup, one-way HMAC verifier, hard 24-hour expiry and status-only response; both results are private/no-store with uniform 404. | Preserves accepted privacy contract. Credential strength/generation, key lifecycle, comparison/expiry controls, exposure and abuse controls, and residual-risk acceptance remain open under O4/O5. |
| Sandbox terminal outcomes are backend-controlled and deterministic; demo failure is explicitly labeled, with no ETA or real-settlement promise. | Keeps simulation truthful and prevents donor-selected results. |
| Guest email requires ownership verification and uses a durable idempotent terminal outbox. | Prevents premature or duplicate notices; operational bounds, provider, retention and residual-risk evidence remain open. |
| WU-S2-003 owns accepted Campaign draft create/PATCH and minimum membership/eligibility persistence. | This is delivery routing only. It does not establish authority to set/update Organization truth or authorize the affected handlers. |
| Request idempotency uses a keyed HMAC over the complete canonical request including PII; no raw request JSON is stored and fingerprint is deleted with its bounded record. | Keeps retry equivalence after optional PII deletion; the bounded record lifetime must be set under O3. |
| Funding-unavailable admission fails closed with generic `503`, no internal reason or `Retry-After`. | Prevents absent Funding from being treated as zero; accepted API counterparts do not prove backend runtime behavior. |
| Proposed D1 migration is additive after `000012`, with restrictive Campaign FK and nullable legacy close reason. | Protects financial/retry/terminal history and avoids fabricated legacy close reasons. F-02/F-03/F-04/F-06 remain subject to a fresh positive design Review; no reversibility or lock behavior is claimed. |
