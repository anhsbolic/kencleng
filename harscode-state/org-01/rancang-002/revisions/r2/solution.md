## R2-A — Identity, concurrency dan proof-of-control

Semua account-dependent reads/mutations memerlukan account ada dan tidak fenced; session check tanpa account check tidak cukup. Lock order universal: **provider identity advisory lock bila diperlukan → account row → session row (ID urut bila >1) → request lock/receipt/org rows**. Create mendapat account lock sebelum session/request. Refresh/logout juga account dahulu; tidak ada jalur mengambil identity lock sesudah account. Deletion mengambil identity lock untuk mapping Google dahulu lalu account; callback memakai identity lock yang sama sebelum lookup/provisioning. Gunakan transaction locks PostgreSQL, bukan mutex proses untuk account. Identity module menyediakan operasi lintas-module dalam satu `pgx.Tx`; organization tidak melakukan SQL bypass identity.

Create yang commit sebelum delete masuk dependent-set revalidation; create yang menunggu delete tidak menemukan account dan ditolak. Delete tidak diam-diam menutup org yang belum dikonfirmasi. Bila create lebih dahulu menambah org sejak preview, delete 409 `deletion-scope-changed`, tanpa journal intent/erase. Delete lebih dahulu mem-fence account: create/retry/read/refresh/logout yang terlambat tidak memberi authority/effect baru; JWT yang belum exp tidak cukup. Replay revocation yang menang sebelum create menolak create; create yang menang tetap attributed sampai explicit closure. Tidak ada retroactive success cancellation.

Fresh proof adalah **Google flow baru yang dimulai pengguna**, dengan state/nonce/PKCE/browser binding r1, mapped ke **account yang sama**, bukan email cocok atau hanya klik link email. `POST /auth/google/attempts` menerima tambahan body tertutup `{purpose:"deleteAccount"}` untuk authenticated principal (default body `{}` tetap normal login). Attempt menyimpan expected account ID, purpose dan start time; callback wajib mapping yang sama dan account masih efektif, lalu mencatat `deletion_verified_at` pada session baru. Tidak membuat/merge account pada special-purpose callback; mismatch/cancel ditolak aman dan preview lama invalid. Fresh-flow timestamp <=5 menit saat preview, <=10 menit saat confirm; preview expiry10m, satu per session mengganti preview sebelumnya. Ini batas teknis untuk action-specific proof, bukan klaim Google memaksa password/MFA atau policy numerik hukum. Refresh tidak memperbarui proof timestamp. Timeout mengharuskan flow eksplisit ulang.

Stale **normal** unauth login attempt juga penting: memory attempt punya `started_at`; callback dengan identity matching deletion journal cutoff menolak attempt yang dimulai **sebelum atau sama dengan** intent cutoff. Ketika intent belum applied, semua callback identity tersebut ditahan; restart membuang attempts r1. Sesudah active erase confirmed, user boleh memulai normal login baru; mapping baru mendapat UUID account baru, tanpa org/Owner/session/receipt lama. Ini bukan pemulihan deleted account atau permanent provider ban. Identity HMAC fence di journal hanya selama affected backup masih ada; memory attempts maksimum5m **hingga final provisioning effect**, bukan hanya sampai callback dimulai: verifikasi expiry kembali sesudah Google network I/O dan sesudah menunggu identity/account lock, tepat sebelum lookup/provision/session issuance. Validated payload yang disalin ke variable tidak melewati batas attempt; DB/protocol timeouts membatasi callback dan rollback bila deadline habis. Maka cutoff tidak perlu disimpan permanen. Journal lookup tidak tersedia/unknown → callback provisioning fail closed, bukan dianggap tidak ada marker. Proses callback yang sudah memegang identity lock diselesaikan dahulu; deletion lalu menghapus session baru itu juga.

## R2-B — Verified explicit closure dan active erasure

Identity module owns orchestration; organization module menyediakan `InspectSimpleOwnedContexts(tx,account)` dan `EraseConfirmedContexts(tx, exactIDs)` dengan preconditions sama. `account.deleteSelf` allow hanya effective authenticated same account + fresh proof + valid preview + explicit confirmation; backend mengevaluasi full dependency set, bukan role/body accountId. Tidak ada service grant baru.

1. Preview locks account untuk snapshot primary DB, validates proof, dan enumerates **seluruh** dependent organizations. Preview menggambarkan IDs/names, Owner internal, penghentian semua sessions/akses, active erasure dan copies/backup yang tersisa dengan batas yang sudah diputuskan. Nol org adalah set kosong yang sah. Detail dikirim hanya ke principal tersebut. UI harus menampilkan seluruh set sebelum confirm; tidak truncate daftar lalu menyebut “semua”. Maksimum satu response <=64 KiB; bila set tidak dapat direview lengkap dalam bound, hasil `manual-review-required`, tanpa preview actionable; bukan penolakan hak privasi atau kewajiban org-count Product.
2. Simple eligibility pada baseline ini: setiap org tepat `first_owner=account`, tanpa other-user relationship, Campaign, transaction atau additional obligations; tidak ada dependency tersebut pada intended schema saat ini. Implementasi harus menyediakan registry eksplisit pemeriksaan semua FK/domain references yang benar-benar ada saat adoption, bukan menganggap “hanya ada first_owner” selamanya. Unknown feature/dependency/foreign references → fail closed simple operation, masuk manual handling. Tidak menginventasikan aturan closure kasus kompleks.
3. Preview DB record menyimpan generated UUID, account/session IDs, sorted org IDs + digest, expiry dan proof time. Tidak menduplikasi names/provider/profile; status hanya `prepared`, tidak bermakna request deletion accepted. Set membership selalu dihitung ulang pada confirm. Body confirm harus `{previewId,closeOrganizations:true}`; untuk nol org nilai true mengonfirmasi set kosong. False/missing/unknown fields bukan permission. Aktor yang ingin organisasi tetap berjalan diberi arah keputusan pengalihan yang belum tersedia; tidak auto pilih pengganti.
4. Confirm reauthenticates, checks CSRF/Origin/JSON, obtains locks R2-A, verifies unused/nonexpired account/session-bound preview; rechecks exact dependent set dan simple predicates. Scope/account/proof berubah →409/401, hapus/invalidasi preview, minta review/proof baru. Tidak ada effect/journal. Confirmed preview jadi immutable intent; tidak menerima perubahan org list dari client.
5. Setelah semua checks, buat journal **durable authorized intent** R2-E sebelum erase. Ini titik penerimaan permintaan dan fence, **bukan bukti erase selesai**. Journal tidak boleh ditulis dari preview/GET/email. Successor retries memakai intent UUID yang sama; sebelum initial append, UUID dibuat server dari preview (one intent per preview). Hold account+identity locks selama append dengan timeout5s; ambiguous journal acknowledgment → rollback active tx, hasil `result-unknown`, fence diperlakukan konservatif sampai reconciliation. Bounded external wait bukan indefinite DB lock.
6. Bila append confirmed, dalam active transaction: delete creation receipts milik account, delete confirmed org rows, delete seluruh refresh rows child-first (successor before predecessor, atau hapus self-FK set secara satu statement yang sah), delete seluruh previews milik account (termasuk preview session lain) sebelum parent sessions, delete seluruh sessions, delete provider mapping(s), delete account. Intent mengikat exact org set dan account. Semua statements melalui owning domain operations dalam transaksi yang sama; FK NOT NULL/RESTRICT tetap final integrity backstop. Unexpected FK/data/dependency → rollback, request pending/fenced, manual escalation dengan outcome jujur; tidak CASCADE/menghilangkan check untuk memaksa berhasil. Active request tidak mengubah nama menjadi “deleted” sambil menyimpan profil.
7. Verified commit membuat **accessEnded=true dan activeDataErased=true** pada saat yang sama; expire cookies, clear FE private caches/markers. Journal application acknowledgment sesudah commit dapat tertunda, sehingga reconciliation membaca primary DB (account/org/session/mapping absent), baru mencatat applied. Ambiguous COMMIT → tidak mengklaim success, reconcilier memakai intent idempotent. Tidak menjalankan ulang creation atau memberi transfer. Bila intent ada tetapi DB rollback, access fence tetap berlaku: accepted confirmed deletion diproses ulang dengan locks/checks yang sama; tidak membuka kembali akses hanya karena erase gagal sementara.
8. Tidak menawarkan automatic cancellation sesudah confirmed durable intent. Bila changed dependency baru ditemukan, account tetap fenced, owner menangani request dan dampak di luar simple flow. Status manual/held harus punya responsible Product/privacy owner, alasan aman, langkah klarifikasi dan follow-up terjadwal oleh operator; tidak dibiarkan tanpa batas. Tidak menetapkan deadline hak hukum baru.

Setelah account erased tidak ada valid session untuk status read. Pilihan paling kecil: response confirm yang terverifikasi menyatakan active outcome/copies pending; **tidak ada authenticated GET setelah penghapusan, public UUID bearer status, email receipt otomatis, atau session khusus yang diam-diam dipertahankan**. Bila response hilang/503/401 setelah intent, UI menyatakan hasil belum diketahui dan mengarahkan care@ untuk follow-up terverifikasi; tidak menyebut gagal atau meminta login untuk melihat account lama. Kasus follow-up operator/read-only request inspection memerlukan prosedur terbatas yang disetujui dan bukti readiness sebelum release; case UUID/correlation hanyalah referensi, bukan bukti identity atau authority. Jangan auto normal-login setelah delete; itu dapat membentuk akun baru yang berbeda.

## R2-C — Retensi, safe retry dan cleanup

| Kategori / owner | Batas dan mekanisme |
| --- | --- |
| Account/mapping/org/Owner/name / identity+organization | Selama tujuan layanan/inspectability aktif; simple verified deletion R2-B menghapus active rows. Kasus lain tidak diberi indefinite exemption; owning lifecycle keputusan fitur terkait masih diperlukan. |
| Successful creation receipt / organization | Tambah `succeeded_at` server time pada final insertion dalam transaction + `expires_at = succeeded_at + interval '48 hours'`; immutable. Successful creation instant wire/org `created_at` memakai instant ini. Receipt readable/replayable hanya `now < expires_at`; hapus pada batas48h, tanpa tambahan 24h cleanup atau reset pada retry. Ini logical effective creation instant transaction yang commit, bukan waktu HTTP response. Tidak menyimpan attempt gagal. |
| New-effect retry / organization | UUIDv7 timestamp <=now+5m dan **absent-key admission** hanya sampai encoded timestamp+24h. Recheck sesudah semua lock waits. Transaction admitted dibatasi DB timeout30s total termasuk lock wait, idle-in-transaction5s, lock wait2s; external commit-ack ambiguity tetap unknown. Cleanup/expiry tidak memberi efek baru. Receipt yang sudah expired tidak replay; absent expired key →410 tanpa effect. |
| In-flight/cleanup / organization | Receipt48h jauh melampaui key24h+5m skew+30s bounded transaction. Cleanup mengambil account/request serialization yang sama atau DELETE committed expired rows tanpa menghapus in-flight row; uncommitted insert tidak terlihat, DB timeout membatasi kelangsungannya. Receipt creation time tidak dimundurkan ke key timestamp. Tidak pernah prune receipt masih dalam admission/in-flight interval. Bila engine/time/bound tidak dapat dibuktikan, fail closed new-effect admission dan release hold, jangan memperpanjang receipt. |
| Earlier receipt erasure / organization | Account deletion boleh sebelum48h: seluruh old account authority erased/fenced bersamaan; no same-account retry/provision resurrection. Tidak perlu menyimpan full receipt sebagai pengecualian hak. New login UUID baru tidak membawa marker/key: FE key terikat old account dan tidak resend setelah mismatch. POST old JWT ditolak; old GET tidak mengekspos nama melalui receipt. |
| Session/family/refresh / identity | Absolute family30d, idle7d, access5m tetap proposal validitas. Parent+consumed verifier dipertahankan hanya selama family bisa dipakai/deteksi replay; hard purge **<= family-created+30d+24h**, tidak sliding30d dari refresh terakhir. Logout/replay-revoked/idle-expired: karena session DB check menolak dan session UUID tidak dapat dihidupkan kembali, hapus seluruh session-bound previews dahulu, lalu refresh verifiers/CSRF/session setelah active transactions selesai, target cleanup dalam24h dari termination dan lebih cepat pada delete. Tidak menahan ended family sampai30d hanya karena maksimalnya30d. |
| Login attempts / identity | Memory max5m, one-use; purge saat consumed/expired/restart. Preview max10m, hapus saat invalidated/consumed/expiry, tidak punya 48h receipt retention. |
| Necessary security/diagnostic logs / deployment | Maksimal14d sejak event, termasuk exports/rotated files/collector copies. No names/provider IDs/profile/token/full payload. Correlation/outcome minimum; tidak menambah audit platform/IP/UA tracking. Tidak mengklaim anonymization pada UUID. |
| Backups / deployment-data owner | **Seluruh** base/full/incremental/WAL/snapshot/export/replica-archival/provider recovery copies harus memiliki umur artifact/recovery point asal <=14d, dihitung dari original capture/base-chain yang masih diperlukan, **bukan umur business row**. Fresh backup boleh memuat active rows yang sudah berumur>14d selama tujuan penyimpanannya masih berlaku. Copy/export/replication backup lama tidak mereset origin age. Base chain berumur>14d tidak boleh dipertahankan walaupun incremental terbaru masih muda. Pilih provider policy yang dapat membuang chain dan dependents atau mengganti base sebelum deadline; tidak memilih provider/frekuensi/RPO/RTO di sini. Backup bukan sumber operasi biasa. |

Cleanup adalah kebutuhan nyata baru: satu bounded maintenance operation per owner, dijalankan scheduled **terpisah dari REST API** sesuai T01 (authorized Worker/one-shot maintenance runner, bukan background goroutine API). Tidak memilih queue/scheduler/vendor. Reads menegakkan expiry walau cleanup gagal; **read exclusion bukan bukti physical erasure**. Operator harus membuktikan penghapusan durable record/copies pada deadline, termasuk saat maintenance/down time; detection overdue menahan privacy-compliance/status claims dan memicu perbaikan, bukan diam-diam grace period. SQL DELETE saja juga bukan bukti sanitasi WAL/dead tuples/media; actual provider storage/reclamation/encryption and backup evidence harus mendukung arti penghapusan yang akan dijanjikan notice. Jika deadline48h/14d tidak dapat dipenuhi oleh actual platform, eskalasi constraint ke owner sebelum real data, jangan menyatakan desain durasi sebagai verified outcome.

GET receipt yang absent/expired =404 `result-not-observed`, bukan failure/cancellation; original mungkin sudah commit, current own-list/detail masih tersedia selama active. POST old key expired =410 `request-window-expired`, bukan bukti original rollback. Tidak automatic fresh-key retry. Existing receipt replay masih memeriksa current relationship dan account, tidak memulihkan closed context. Own-list/detail tidak memakai retained receipt sebagai sumber authority.

## R2-D — Minimal data/contract impact dan migrasi

Pertahankan regular public tables/nonpartitioned, `first_owner_account_id NOT NULL FK accounts RESTRICT`, composite attribution FK dan seluruh unique/check r1. **Tidak perlu nullable initial Owner, tombstone account pengganti atau generic membership table.** Deletion menghapus receipt sebelum organization sebelum account; intended schema tetap membuktikan setiap active org memiliki actual Owner. Closure tidak mempunyai row active yang kehilangan attribution. Bila durable closure history kelak dibutuhkan Product, itu keputusan baru, bukan menyimpan name/Owner diam-diam.

Tambahan scoped fields:

- `auth_sessions.deletion_verified_at TIMESTAMPTZ NULL` hanya proof special flow; nullable means not verified, bukan default true. Normal auth/refresh tidak mengisinya.
- `organization_creation_receipts.succeeded_at/expires_at TIMESTAMPTZ NOT NULL`, CHECK expires_at=succeeded_at+48h; expiry index. Tidak menyimpan payload fingerprint tambahan karena immutable org name tetap sumber exact-name replay selama active.
- `account_deletion_previews`: `id UUID PK`, `account_id FK accounts RESTRICT`, `session_id FK auth_sessions RESTRICT`, `organization_ids UUID[] NOT NULL` (sorted unique, boleh kosong), `set_digest BYTEA NOT NULL`, `expires_at TIMESTAMPTZ NOT NULL`; digest computed server from sorted IDs/current eligibility version, **bukan anonymization**. Max response/persisted set bound64KiB; unique session preview. Referential ownership/divergence diperiksa server, tidak percaya array client. FK session-account consistent melalui composite reference; no cross-account preview.
- Memory login attempt menambah `started_at`, `purpose`, optional `expected_account_id`; no stored profile. All additions Confidential pseudonymous/Restricted proof metadata; protected DB/memory, backend only except own preview ID/expiry/actual org summaries. No names duplicated in preview/journal.

Journal R2-E berada pada protected store di luar rollback domain active DB, dengan access hanya identity erasure/reconciliation dan restore operator yang diauthorisasi; tidak diekspos raw ke API, logs atau generic analytics. Record minimum: `intentId UUID`, old `accountId UUID`, exact organization UUIDs, `confirmedAt`, identity fence `HMAC(dedicated key, canonical issuer+subject)` + key version, immutable applied checkpoint bila tersedia, affected-backup expiry evidence reference. HMAC perlu plaintext issuer+subject hanya di identity processing; tidak menyimpan provider raw/profile/name/email. Ini pseudonymous personal metadata, purpose deletion/restore, bukan anonim. Journal key purpose-separated dari JWT/CSRF; T04 custody/rotation. Mapping/linking lain belum aktif; bila ada saat adoption enumerate seluruh verified identities, bukan hanya Google pertama.

Preview berlaku <=10m; marker hanya selama affected backup masih ada + unresolved accepted execution membutuhkan fence. Unresolved execution harus ditangani segera dengan follow-up, bukan unlimited marker allowance. Sesudah active applied dan semua affected backup/chain copies terbukti expired, hapus marker/fence/ack dan related exported copies; no arbitrary extra14d sejak acknowledgment. Marker tidak masuk log retained14d sebagai duplicate identity trail. Unresolved exception butuh owner decision, bukan hidden indefinite hold. Saat tidak ada backup, marker dibuang setelah verified application dan pre-delete attempts pasti expired (maks5m), tanpa 14d minimum.

Actual schema belum ada. Downstream membuat versioned SQL fresh installation; jika baseline sudah berubah saat adoption, introspeksi actual constraints/data dan rancang upgrade/backfill succeeded_at dari **known original creation instant**, bukan current time yang memperpanjang retention. Tidak dapat mengetahui instant → held migration edge, bukan fabricate receipt. Deploy compatible producers/cleanup sebelum expose deletion; enforce account lock order di semua callers. Rollback schema tidak boleh menghidupkan deleted accounts/orgs/receipts; irreversible erasure tidak punya down-migration resurrection. Tidak menjalankan migrations/reset sekarang.

## R2-E — Vendor-neutral journal dan restore safety contract

Minimum journal interface: `PutConfirmedIntent(intentId, immutablePayload)` idempotent exact equality; mismatch rejected; returns durable acknowledgment atau unknown. `FindByIdentityFence/Account/Intent` linearizable/current enough to enforce fences; unavailable → refuse affected protected action/provisioning. `MarkApplied(intentId, checkpoint)` hanya sesudah current primary inspection; `EnumerateConfirmedAfter(restorePoint)` lengkap dengan independent monotonically ordered coverage watermark. Durable intent tidak dihapus/ditandai cancelled oleh rollback active DB. Provider choice harus membuktikan atomic record write, survives selected DB rollback/loss, custody, visibility/concurrency, retention and completeness. Tidak menyamakan ordinary DB backup sidecar dengan independent coverage.

| Failure point | Current handling dan honest status |
| --- | --- |
| Sebelum intent append, SQL rollback | Tidak accepted, active account tetap ada; caller dapat mulai preview baru setelah memastikan kondisi. |
| Append acknowledgment unknown | Active erase tidak dijalankan tanpa confirmed durable append; UI unknown. Reconciliation queries same intentId; absent yang definitif berarti tidak accepted; present berarti accepted/fenced dan apply. Bila journal tak dapat memastikan absent/present, tetap unknown/held, bukan “gagal”. |
| Durable intent, crash/rollback sebelum erase commit | Request accepted, fenced; current reads/mutations/login yang relevan ditolak. Reconciliation mengambil locks dan idempotently applies exact confirmed simple deletion, tidak perlu user session yang sudah dicabut. Ini execution of explicit user intent, bukan arbitrary operator authority. |
| COMMIT acknowledgment unknown | UI unknown; account/org/session absence di primary + intent menentukan applied, bukan process log. Masih ada rows → retry same intent/checks, no duplicate org effects. |

Per-account fence harus dicek oleh semua protected boundaries setelah memperoleh account lock; missing identity mapping **tidak** otomatis berarti aman membuat account bila journal belum diketahui. Journal failure bukan alasan membuka access. Downstream T03 permission inventory+deployment custody harus membatasi principal ini sebelum authorized execution; tidak ada tool/credential dibuat dalam assignment ini.

Restore minimum, sebelum traffic/API callbacks/Workers/egress dibuka: (1) isolate restored DB, secrets/caches/queues dan side-effect senders; (2) pastikan restore point dan **independent journal coverage sampai cutover** lengkap; bila gap/unknown, remain closed; (3) reapply seluruh confirmed deletion intents yang dapat memengaruhi restored rows, termasuk pending/unknown-ack intents, dengan owner dependency checks; tidak cukup applied-only rows; (4) hapus seluruh restored app sessions/refresh/previews dan memory login attempts, invalidate access via live-session check; rotate/disable restored credentials sesuai custody supaya revoked access tidak hidup kembali; (5) purge expired receipts/log/copies dan refuse absent expired keys, flush private caches; (6) verify old account/org/mapping absence, old JWT/refresh/callback/retry rejection, journal watermark stability under concurrent deletion cutoff, dan outbound replay nonexecution; baru release traffic. Tidak menjalankan recovered jobs/creation dari backup. Tidak perlu menyimpan historical revocation journal untuk setiap logout: **semua sessions direvoke pada restore**. Normal fresh login sesudah restore mengikuti cutoff dan mapping terkini, tidak memulihkan erased account.

Deletion baru ketika restore berlangsung harus masuk journal watermark sampai atomic admission cutover; maintenance freeze deletion writes pada cutoff singkat atau drain-and-recheck journal tanpa gap sebelum membuka traffic. Jika tidak bisa menjamin itu, layanan tetap closed. Representative restore evidence harus mencakup deletion sesudah backup, pre-delete auth attempts, ambiguous commit, expired receipts dan lost session revocation. Tidak ada production recoverability claim dari pseudocode ini.
