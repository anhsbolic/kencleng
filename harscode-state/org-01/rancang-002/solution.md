### Biaya surface dan alternatif

Empat operasi organisasi dipilih untuk kebutuhan terpisah: create melakukan efek; receipt lookup mengidentifikasi exact attempt setelah lost response tanpa mengirim mutation; own list menemukan kembali organisasi ketika key/link hilang (termasuk perangkat lain); detail adalah stable per-org independent current inspection setelah memilih list atau Location. List + receipt saja bisa mengurangi satu read route, tetapi memaksa mencari semua halaman untuk direct organization revisit. Detail + receipt saja gagal discovery setelah key/link hilang. Create + own list saja bisa memenuhi inspeksi tetapi exact unknown attempt tetap ambigu ketika beberapa nama sama. Maka receipt adalah delegated safeguard untuk duplicate action, bukan requirement recovery Product. Tidak ada status polling service, history, search, update/delete/transfer atau general dashboard. Jika downstream acceptance sengaja memilih uncertainty-only tanpa exact attempt recovery, count dapat diperkecil melalui review accepted contract, bukan diam-diam mencabut safeguard.

### Alternatif dan konsekuensi

- Dua transaksi org lalu Owner ditolak: menambah orphan/partial result dan compensation tanpa manfaat. Satu row organisasi dengan `first_owner_account_id NOT NULL` dipilih sebagai assignment Owner scoped, alih-alih generic membership/role tables. T03 memperbolehkan physical model sesuai domain; assignment tetap durable, permission policy di code. Jika perpindahan/revoke/multi-Owner kelak diotorisasi, model harus ditinjau ulang; tidak boleh menyulap field initial menjadi global role.
- Pure POST tanpa receipt lebih sedikit tabel, tetapi lost response berisiko duplikasi atau tak bisa mengidentifikasi attempt. Receipt lokal dalam transaction dipilih; tidak membangun job recovery/status platform. General dedupe berdasarkan nama ditolak oleh REQ08.
- Sign-in sebelum nama dipilih dibanding popup yang mempertahankan preauth form: urutan awal memberi biaya sign-in lebih dini tetapi menghilangkan cross-window lifecycle/focus/blocked-popup dan draft PII. REQ01 mengizinkan memulai tanpa klaim legal proof, tidak mewajibkan mengisi nama sebelum login. Experience menantang kompleksitas popup; Architect menerima alternatif lebih kecil. Tidak ada server/browser draft nama atau klaim cross-device draft.

## O2 — Prasyarat identity/session yang konkret

Owning responsibility: modul identity mengelola account/provider mapping/session; modul organization mengelola organisasi/Owner dan receipt. Shared DB adapter hanya plumbing. Organization operation menerima trusted `{accountId, sessionId}` dari identity boundary lalu rechecks session efektif dalam transaction; tidak menerima actor/role dari body.

### Login dan session lifecycle

1. Same-origin user gesture membuka `POST /auth/google/attempts` (strict exact allowed Origin, `application/json` dan penolakan simple/form content types, tanpa cross-origin CORS grant; origin+JSON adalah defense pre-login, dilanjutkan browser-bound state/nonce/PKCE pada callback). Backend membuat random state, nonce, PKCE verifier; verifier/state secrets hanya server-side, bounded expiry lima menit, satu kali pakai. Response `201 {data:{authorizationUrl}}`; URL hanya destination Google allowlisted dengan state/PKCE challenge, bukan application token. FE mengarahkan browser pada URL ini sebelum field nama dibuka. Login dimulai dari aksi eksplisit, tidak dari GET prefetch. Provider access/ID tokens tidak pernah masuk JS.
2. Google authorization-code flow backend callback `GET /auth/google/callback?code&state`; ini protocol exception untuk GET callback, **hanya** menukar login session, tidak melakukan organisasi mutation. Browser-bound state cookie + server attempt dicocokkan, atomic single consumption, nonce/PKCE dan issuer/audience/signature/expiry ID token divalidasi menggunakan maintained OIDC library. Redirect URI exact allowlist, no arbitrary `returnTo`. Google `sub` dengan canonical validated issuer menjadi mapping; email/display name/picture/phone tidak diminta/disimpan/di-output. Scope `openid` cukup; tidak menambah `email profile` tanpa approved purpose.
3. Transaction identity menggunakan unique `(issuer, subject)`; bila first login, buat UUID account dan mapping atomically, concurrent unique race rollback lalu read existing mapping. Tidak merge by email. Satu internal account dapat punya banyak identity secara logical, tetapi linking endpoint tidak dibuat. Google provider tokens dibuang setelah validation; tidak meminta offline access atau menyimpan refresh Google.
4. Backend menerbitkan access JWT dan opaque random 256-bit refresh cookie, tidak mengembalikan raw token dalam JSON/URL/postMessage. JWT proposal scoped: `RS256`, allowlisted trusted `kid`, private signing key purpose-separated dari semua key lain, claims `iss`, `aud`, `sub=account UUID`, `sid`, `iat`, `exp`, tanpa role/PII. Access lifetime proposal lima menit; refresh idle tujuh hari, absolute tiga puluh hari. Angka dan library/key custody diperiksa Security sebelum protected implementation; bukan kebijakan proyek baru. Public key rotation mempertahankan key verifikasi lama hingga access tokens terkait expired; unknown `kid` ditolak tanpa arbitrary fetch dari header JWT. Kunci tidak dibuat pada setiap startup.
5. Semua protected requests memverifikasi JWT lengkap dan effective session (revoked/expired/account match) dari DB; ORG create merecheck/lock session row sampai commit. Logout/replay revocation memakai row lock yang sama sehingga urutan effect eksplisit: revocation yang commit lebih dahulu menolak create; create yang commit lebih dahulu tetap teratribusi sah. Tidak mengklaim pembatalan retrospektif.
6. Refresh token format opaque random; verifier SHA-256 dari entropy tinggi, constant-time comparison; raw tidak disimpan. `auth_refresh_tokens` menyimpan predecessor history sampai family absolute expiry untuk mendeteksi reuse. Refresh transaction mengunci session, memvalidasi idle/absolute/revocation dan unused predecessor, marks consumed, inserts successor dan updates session idle deadline atomically. Reuse token yang consumed mencabut seluruh session/family; tidak ada grace replay window. Concurrent refresh hanya satu successor, loser mencabut family; FE wajib single-flight per tab dan koordinasi lintas tab bila tersedia. Lost refresh response/race dapat memerlukan Google sign-in ulang; UX menyatakan session tidak berlaku, tidak mengulangi create dengan key baru. Ini trade-off fail-safe yang harus diuji.
7. Logout revokes session+refresh authority dan expires cookies; safe repeated logout `204`, termasuk session yang sudah hilang, tetapi tetap Origin/CSRF guarded. CSRF tidak diganti SameSite/CORS: untuk authenticated mutation gunakan strict exact Origin dan `X-CSRF-Token` session-bound yang backend expose lewat session API. Konstruksi recoverable tanpa menyimpan raw browser token: simpan random `csrf_nonce` 256-bit pada session; derive token base64url HMAC-SHA-256 dengan dedicated backend CSRF key atas domain separator + session UUID + nonce. Server recomputes dan constant-time compares; key terpisah dari JWT/PII, tidak di browser. GET session dapat mengeluarkan token sama setelah reload; stable per session selama refresh sehingga concurrent tabs tidak saling menginvalidasi. Logout/replay revocation menonaktifkan session/CSRF bersama. CSRF-key rollover boleh invalidasi token lama, client re-GET session sebelum explicit mutation ulang; jangan replay mutation dengan fresh key. Missing/null/wrong Origin ditolak; accepted JSON content type saja, body bounded. Refresh menggunakan cookie+CSRF; CSRF token bukan auth secret dan tidak memberi akses tanpa cookie.

Cookie policy: host-only tanpa Domain, HttpOnly, SameSite=Lax, access Path=/api (browser ingress), refresh Path=/api/auth; route/session cookie scope harus mencakup session API/callback response issuance melalui ingress. Backend routes tetap unprefixed; browser `/api` prefix milik gateway. Non-local wajib HTTPS Secure=true dengan explicit trusted-proxy config; local HTTP hanya effective local + actual loopback ingress, tanpa secure-prefix yang tidak kompatibel. Default Secure=true; insecure invalid config fail startup. Nonlocal routing belum ditetapkan: sebelum deployment ingress wajib memastikan prefix/Path sesuai dan kedua cookie tidak collision. Auth attempt cookie juga host-only HttpOnly SameSite=Lax, callback-path scoped pada ingress; five-minute expiry. `Cache-Control: no-store` pada semua auth/private responses; callback `Referrer-Policy: no-referrer`, redirect fixed completion page, query/token redaction di ingress/logs.

Callback mengakhiri pada fixed same-origin continuation page tanpa token; FE mengonfirmasi principal melalui `GET /auth/session`, lalu baru menampilkan field nama. Cancel/IdP gagal: tidak ada business effect, beri aksi sign-in ulang. Sesudah nama diisi, expiry/session failure tidak menavigasi otomatis: input tetap di memory sambil aktor memilih tindakan. Jika aktor memilih full-page reauthentication, UI lebih dahulu menjelaskan bahwa nama harus diisi ulang; pending marker account/key tetap bisa dipakai untuk memeriksa attempt. Reauth/switch account menghapus private query caches dan mewajibkan review ulang target/principal. Tidak auto-submit sesudah login/refresh.

## O2 — Data, relasi, privacy

Logical ERD tanpa full-product schema:

```text
accounts 1 --- N authentication_identities       UNIQUE(issuer,subject)
accounts 1 --- N auth_sessions 1 --- N auth_refresh_tokens
accounts 1 --- N organizations                  first_owner_account_id NOT NULL
accounts 1 --- N organization_creation_receipts N --- 1 organizations
auth_login_attempts -- browser-bound one-use login state (sebelum account diketahui)
```

`organizations.first_owner_account_id` adalah relasi Owner internal yang durable, bukan klaim external/legal; satu organization tepat satu initial Owner pada scope ini. FK langsung membuat organisasi tak teratribusi mustahil dalam intended schema. Tidak perlu table role/membership generik untuk satu assignment. Timestamps untuk effective creation/session/expiry punya purpose nyata, tidak semua tabel mendapat arbitrary updated_at.

| Table/owner | Fields dan constraints usulan |
| --- | --- |
| `accounts` / identity | `id UUID PK NOT NULL`. Tidak ada mandatory email, nama orang, status eligibility atau soft-delete. |

## O2 — Create transaction, retry dan hasil belum pasti

Organization module owns transaction orchestration; identity exposes session check/lock usable on same `pgx.Tx`. No network call to Google inside transaction. Use PostgreSQL READ COMMITTED plus unique receipt key and row lock; not global SERIALIZABLE or distributed locking.

1. Validate JSON schema and name canonicalization: trim Unicode whitespace at edges, preserve case/internal whitespace, 1–200 Unicode code points, reject NUL/control characters; request <=4 KiB, unknown fields rejected. Return canonical name in review UI before submission; client/backend normalize identically but backend authoritative. No uniqueness check. Technical length/control bound is scoped input safety, not legal eligibility.
2. Authenticate JWT and live session, then begin DB transaction and lock session row; verify still effective at current server time. Account ID comes solely from principal.
3. Require UUIDv7 request ID; timestamp must not exceed server time by >5 menit. Absent-receipt key hanya boleh menciptakan efek sampai 24 jam dari encoded timestamp (technical retry window, bukan Product retention duration). Key lebih tua ditolak 410 `request-window-expired` tanpa mutation; existing visible receipt tetap boleh dibaca/replay tanpa membuat efek. Tidak menerima UUIDv4/opaque timestamp yang tidak dapat dibatasi. FE menggunakan key baru saat intended submission dimulai, bukan pada setiap retry. Serialize same `(accountId,requestId)` using transaction-scoped PostgreSQL advisory lock derived from both UUIDs (fixed deterministic hash, parameterized; collision only serializes unrelated requests, never merges identities). Re-read receipt under READ COMMITTED. Unique PK is final correctness backstop. Lock order session then request consistent everywhere; request lock wait bounded.
4. Existing receipt: compare incoming canonical `name` to immutable creation name in referenced organization. Same name -> return existing result after current visibility and pair validation; different name -> 409 `idempotency-mismatch`, no change. Name edits are not offered in scope; adding edits later must add immutable request fingerprint/source before reusing this comparison.
5. Absent receipt: recheck key window **setelah** menunggu lock; bila expired, 410 tanpa effect. Jika valid, generate org UUID, insert organization with NOT NULL initial Owner = account, insert receipt in same transaction, COMMIT. No grants supplied by client, no Reviewer/external/publication side effects. Verified commit -> 201 pair with Location; repeated same key -> 200 same org ID. Response representation includes current owned pair, not success flag.
6. SQL/constraint failure before known commit -> rollback, no org/receipt effect; expected error mapped safely. Serialization/deadlock may be retried backend at most once for known rollback with same key; never blindly retry ambiguous COMMIT. DB loss/timeout after COMMIT sent -> unknown, return 503 `result-unknown` if response possible; transport loss likewise unknown. Logging uses correlation ID/outcome category, not name/tokens.
7. `GET /organization-creation-requests/{requestId}` queries primary durable DB under authenticated account, joining receipt+org+owner. Committed valid pair -> 200 confirmed result; absent row -> 404 `result-not-observed`, explicitly **does not prove failure/cancellation** because original transaction may still commit. No 202 fake pending row. Incomplete invariant -> 503 `result-unavailable`, never half-success. Current permission loss -> same unavailable 404 semantics, not old receipt content.
8. Actor may check again or intentionally retry exact same key/account/name; advisory lock/PK prevent second org even if original is in flight. No auto fresh-key retry on timeout/401/5xx/404. GET after successful create reads primary (no replica/read cache) with `no-store`; initial response alone is not permanent current-state evidence.

Bounded own-org list/detail resolves later inspection even after browser marker loss. Matching name in list does not establish that a particular unknown attempt committed; display distinct IDs and no auto-merge. If payload/key lost, do not claim exactly-once recovery; show current owned contexts and uncertainty. Distinct keys mean distinct intent even from two tabs; no hidden per-account name lock. No indefinite polling; first user-driven check/retry, UI may perform one result check on timeout then retain explicit unknown state. Receipt tidak boleh dihapus selama key masih dapat diterima untuk new effect (termasuk bounded in-flight lock/commit interval). Missing expired receipt tidak pernah menjadi efek baru: POST wajib 410. Jika original sempat mulai sebelum expiry, 410 pada retry/404 read tetap bukan bukti bahwa original rollback. Cleanup/lifecycle policy tidak boleh membuka kembali jendela; bila record sengaja dihapus sebelum window berakhir, pertahankan minimal account/key tombstone sampai window tutup atau fail closed create untuk rentang terdampak. Detail cleanup baru boleh diimplementasikan sesudah PD-PRIV-01, tanpa mengarang indefinite business retention.

## O2 — Proposed API surface for downstream canonical adoption

All paths below are backend unprefixed; browser development uses `/api` rewrite. **Proposed only**, no edits to `api/`. Canonical adopter must encode OpenAPI 3.0.3 with cookie security, CSRF headers, required/nullable fields, schemas/statuses and tests before FE/BE consume generated types. No external API versioning/service client capability implied.

Common wire shapes (camelCase, closed objects, UTC RFC3339 instants):

```json
{"data":{"organization":{"id":"uuid","name":"Nama dari aktor","createdAt":"2026-10-29T00:00:00Z"},"owner":{"accountId":"uuid","role":"Owner","scope":"internal"}}}
```

`OrganizationResult` above contains only non-null fields; owner is the current requester’s actual scoped relationship. Tidak ada nama orang/profil, foto, email, provider subject atau verification status; `organization.name` tetap nama konteks yang diberikan aktor. UI renders fixed explanatory meaning from O3, not invented external claims. `role` is enum Owner and `scope` enum internal, descriptive output only. Client cannot supply them. `CreationResult` adds `requestId UUID` to data alongside organization/owner. Detail lacks requestId. List is `{data:[OrganizationResult],meta:{nextCursor?:string}}`; omit absent cursor/meta when no next page. Empty `data:[]` truthful.
