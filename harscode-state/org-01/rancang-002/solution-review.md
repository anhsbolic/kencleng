## Penilaian trade-off dan total cost

- **Auth prerequisite cukup dan dibatasi:** baseline belum menyediakan identity/session; T02 mengikat Google-only, internal account dan rotating-refresh cookies. Menghapus prasyarat itu akan menghilangkan attribution/security floor. Full role platform, account linking/recovery, external clients, Worker dan broker tidak dibangun. Per-session DB check + lock memberi revocation-sensitive boundary konkret dengan biaya query/serialization; proporsional untuk protected create.
- **Sign-in sebelum name entry direkomendasikan:** public start/meaning tetap tersedia. Alternatif popup memberi preauth editing tetapi membawa blocked-popup, focus, cross-window dan restart states. Lebih awal login adalah biaya aktor nyata; tidak ada requirement bahwa name entry mendahului login. Pilihan ini menghindari persisted name draft serta privacy burden, tanpa auto-submit setelah callback. Reciprocal challenge mengubah pilihan Architect, bukan sekadar review kosmetik.
- **Satu `first_owner_account_id` cukup pada scope:** FK NOT NULL menyatukan attribution dan organization, dengan policy code dan current relationship DB. Generic membership/role tables lebih mahal tanpa kebutuhan additional grants. Ini tidak otomatis mendukung transfer/multi-Owner/revoke workflow. Scope baru harus meninjau ulang schema, receipt comparison dan authorization, bukan menganggap field initial immutable sebagai full role system.
- **Atomic synchronous pair + receipt direkomendasikan:** dua transaksi/saga menambah orphan/compensation. Receipt berbiaya durable state, API dan lifecycle tetapi mengidentifikasi exact unknown attempt tanpa mutation; nama/list tidak dapat membuktikan exact attempt jika sama. Own list diperlukan setelah key/link/device hilang; detail memberi direct current revisit tanpa scan semua pages. Ini minimum berbeda untuk exact-attempt recovery dan current discovery, bukan general history/dashboard. Recovery bukan Product obligation tambahan; safeguards dipilih untuk truthful retry dan duplicate risk T05/T06.
- **Retry expiry cukup dengan limit eksplisit:** UUIDv7 window membatasi new effect dari absent old key. Recheck setelah lock wait, no deletion selama acceptance/in-flight window, tombstone/fail-closed bila perlu, dan 410 tanpa fresh-key retry mencegah cleanup membuka duplicate window. Window expiry tidak membatalkan original transaction. Lost key/payload tetap bisa unknown; tidak ada klaim universal exactly-once recovery. Tambahan clock/key errors diterima sebagai biaya safeguard dan memiliki EXP/TECH obligations.
