## Kebutuhan minimal yang membatasi pilihan teknis

1. Sebelum efek, aktor memahami konteks organisasi yang akan dibuat, dirinya menjadi `Owner` internal pertama, serta batas bahwa hal ini bukan bukti kewenangan legal atau approval Reviewer (REQ03, AC03). Tidak diwajibkan modal, checkbox, wizard, atau jumlah langkah tertentu.
2. Atribusi aktor tersedia saat efek berlaku; memulai tidak harus berarti sudah login atau telah membuktikan representasi legal (REQ01–02). Identitas/kewenangan final mengikuti backend, bukan profil Google yang dibaca browser.
3. Klaim sukses memerlukan pasangan organisasi dan `Owner` awal teratribusi yang benar-benar committed; notifikasi, login berhasil, request dikirim, satu resource saja, atau log bukan penggantinya (REQ04).
4. Aktor bisa memeriksa kembali organisasi dan hubungan `Owner` terkini secara terpisah dari notifikasi dan tanpa bergantung pada transient request key (REQ05).
5. Gagal, partial, tidak teratribusi, dan belum diketahui tidak disamakan dengan sukses. Nama serupa antar-ID tidak memicu block/merge/close otomatis (REQ07–08). Informasi organisasi tetap bersumber dari organisasi (REQ06).

Keinginan yang dapat dinegosiasikan: pengisian sebelum sign-in, persistensi draft lintas-session, history lengkap, recovery otomatis, deteksi nama serupa, dan animasi sukses. Tidak ada yang menjadi Product requirement baru. Outcome tidak membutuhkan full role matrix, Reviewer workflow, Campaign, publikasi, donasi, atau general recovery platform.

Actual O2 binding: identity module memiliki `POST /auth/google/attempts`, callback dan `GET /auth/session`; session result berisi `accountId`/CSRF token, tanpa provider profile. Organization module memiliki `POST /organizations` dengan body name dan account-bound `Idempotency-Key`; 201 create atau 200 exact replay membawa complete `CreationResult`. `GET /organization-creation-requests/{requestId}` 200 memberi observed committed result, 404 result-not-observed tetap unknown, 503 unavailable tidak memberi partial success. `GET /organizations` bounded dan `GET /organizations/{organizationId}` membaca current own pair dari primary DB; unowned/unavailable tidak diungkap melalui hidden detail. HTTP 400/422 membantu validation, 401 auth, 403 defense/denial, 409 payload mismatch, 410 request-window-expired, 429 rate limit dan 503 busy/unknown/unavailable tidak dipetakan ke sukses; UI memakai stable problem type, bukan parsing prose. Seluruh path adalah proposed backend path; frontend dev memakai `/api` rewrite. Canonical adoption tetap terpisah.

O2 memakai UUIDv7 dengan 24-jam new-effect window dan toleransi future timestamp lima menit. Pada 410, replay untuk membuat efek baru ditolak; original attempt mungkin tetap unknown. Jangan mengganti key otomatis atau menyebut window expiry sebagai pembatalan. Receipt yang masih ada dan terlihat tetap dapat diinspeksi/replay sesuai O2; saat record tidak tersedia, current own-org inspection membantu tetapi tidak membuktikan exact attempt. Lifecycle/cleanup bergantung PD-PRIV-01. Key/clock error tidak dijelaskan sebagai nama organisasi salah.

Receipt membuktikan event committed pada original creation; schema output saat ini juga harus lolos current authorization/pair check O2. Jangan menggunakan receipt untuk menyatakan hubungan belum pernah berubah atau mengembalikan privilege. Pada list pagination, empty page berarti tidak ada own context pada scope/query itu, bukan tidak ada organisasi di seluruh platform. Network failure saat read berarti inspection unavailable; cached view bila digunakan harus diberi konteks freshness dan tidak mengizinkan klaim current state baru.

## State lintas autentikasi, reload, dan aksesibilitas

Alur terpilih O1 SOL03: penjelasan/start publik → Google full-page sign-in eksplisit sebelum field nama → backend current-session terkonfirmasi → isi nama/review → submit eksplisit. Setelah autentikasi atau perubahan account, backend current-session harus dikonfirmasi, lalu aktor meninjau akibat dan melakukan submit eksplisit. Jangan melakukan submission otomatis dari callback/login success. Bersihkan hasil/cache privat saat account berubah; request account lama tidak dijalankan ulang sebagai account baru.

Input tetap tersedia di memory pada kegagalan submission biasa/expired session sesuai patterns §4; jangan auto-navigate. Jika aktor memilih full-page reauthentication, jelaskan lebih dahulu bahwa nama harus diisi ulang. Ini explicit transition dengan biaya yang diketahui, bukan silent loss. O2 menyimpan marker pseudonymous `{accountId,requestId}` saja di same-tab sessionStorage sesudah submit; tidak menyimpan nama, profil atau token. Marker bukan authority backend; storage failure berarti reload recovery terbatas, bukan berhasil menyimpan. Pada account mismatch jangan resubmit atau tampilkan private hasil account sebelumnya; bila aktor kembali ke account yang cocok, check receipt/current scope kembali. Reload/tab ditutup bukan janji durable draft. Bila payload hilang tetapi attempt identity tersisa, lookup dapat memeriksa receipt; replay memerlukan payload yang sama menurut aturan normalisasi O2. Bila identitas attempt hilang, discovery current org membantu inspeksi tetapi kesamaan nama tidak membuktikan hasil exact attempt. Nyatakan keterbatasan; jangan membuat sukses atau otomatis membuat request baru.

Frontend memilih DOM/components/route yang paling sempit dari Form, Detail, Status/Tracking, Error/Recovery patterns yang sudah ada. Consequence dan uncertainty tidak tersembunyi oleh progressive disclosure atau layar kecil. State wajib punya label/struktur/konteks, bukan warna atau badge saja. Kontrol dapat dioperasikan keyboard, label field/error berasosiasi, perubahan pending/error/result dapat diketahui assistive technology, serta fokus tetap bermakna setelah auth atau perpindahan state. Ini acceptance interaksi turunan prinsip usability; detail ARIA/focus implementation milik frontend, bukan pola global baru. Jangan menaruh token atau PII tambahan di URL, accessible labels, tooltip, atau error text. Tone tenang dan spesifik; tidak perlu celebration/confetti atau ikon verifikasi.

## Reciprocal challenge dan readiness

Early constraints dikirim ke Architect sebelum O2 settled: keberhasilan pasangan, before-effect meaning, atribusi saat efektif, independent later inspection, truthful unknown dan duplicate identity. Architect membalas minimal name-only, auth-before-effect, atomik pair+receipt, account-bound lookup. Experience menantang dependensi later inspection pada transient key; Architect menerima bounded own-org discovery/detail.

Experience meminta input tidak hilang saat external auth dan account-switch/reload ditangani. Architect menantang persistence nama yang mungkin identifying dan menawarkan memory-preserving popup serta requestId/accountId-only transient storage. Experience menerima sebagai opsi feasible bersyarat accessible return/fallback, lalu menantang biaya cross-window dengan alternatif lebih sederhana: eksplisit sign-in sebelum name entry. Alternatif ini tetap memungkinkan memulai/memahami ORG01 tanpa login dan menghindari draft persistence. Architect memilih sign-in sebelum nama dalam SOL03; O3 menerima keputusan ini setelah membaca actual O2 pada pin di atas. Popup ditolak sebagai biaya tanpa requirement binding. API/UI belum implemented.

Tidak ada remaining O3/O2 disagreement pada checkpoint ini. Bila session/refresh tidak dapat dipastikan, sign-in ulang dapat diperlukan; create tidak diulang dengan key baru, dan logout-unknown tidak diklaim server revocation lengkap. Security/independent review dan Human acceptance belum selesai. PD-PRIV-01 di O2 menahan real-person persistence/lifecycle readiness; O3 tidak memberi consent/legal basis atau retention promise pengganti. Human acceptance, separate implementation authorization dan canonical API adoption tetap gates terpisah.
