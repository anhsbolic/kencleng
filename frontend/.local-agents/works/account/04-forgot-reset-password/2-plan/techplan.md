## 📋 Summary — start here

**What & why** — `docs/spec/1-account/features/04-forgot-reset-password.md` specifies `POST /auth/forgot-password` and `POST /auth/reset-password`, both already built and testable on the backend. Neither has a real frontend form: `app/(auth)/forgot-password/page.tsx` and `app/(auth)/reset-password/page.tsx` are both explicit 12-line placeholder stubs self-labeled "Account Task #4's scope," scaffolded during Phase 0 specifically to be filled in by this task. `login-form.tsx`'s "Lupa password?" link already points at `/forgot-password` and is already tested — the login side of this flow is done and waiting on this task. This plan builds both forms, the API/hook layer behind them, and closes three confirmed contract-drift gaps found by reading the backend source directly during this synthesis (not visible from the frontend-only exploration): a stale generated schema, an undocumented validation branch on `forgot-password`, and a documented-but-never-populated validation branch on `reset-password`.

**Scope** —
- `ForgotPasswordForm` (`/forgot-password`, inside the existing Auth Shell): email field, generic `202` success view, defensive `422` handling, `429`/generic failure banners.
- `ResetPasswordForm` (`/reset-password`, inside the existing Auth Shell — **not** moved to a top-level route, see Decision D1): token-from-URL read, new-password field, terminal `404`/`410` states, non-terminal `422`/`429`/generic-failure banner states, inline success view.
- `lib/api/account.ts` + two new hooks + `mocks/handlers.ts` entries for both endpoints.
- `lib/api/schema.d.ts` regeneration (mechanical — the bundled `api/openapi.yaml` already has `reset-password`'s `429`; only the generated file is stale).
- Out of scope: any backend change (the three drift findings below are flagged, not fixed here); MFA, account linking, or any other Account-domain page; a consolidated backend-copy/i18n cleanup across `/auth/*` (flagged as a follow-up, Open Item #3).

**Decision flow diagram** — skipped. Both forms are linear (idle → submit → one of a small, flat set of terminal/non-terminal outcomes) with no multi-step state machine or cross-component flow where order matters — a table (§4) is faster to scan than a flowchart here, per `rules.md` §7's skip criterion.

**Key decisions** (full rationale in §5):
- D1: `/reset-password` **stays inside the Auth Shell** (`app/(auth)/reset-password/page.tsx`, rebuilt in place) — `frontend/.agents/docs/phase0-shared-infra.md` Step 1 already resolved this specific routing decision; it supersedes the 1-explore Stage 3 recommendation (an analogy from `/verify-email` that didn't see this file), confirmed by Anhar during this synthesis.
- D2: `resetPassword()` resolves/throws plainly (no discriminated validation result) — confirmed directly against `service.go` that its `422` never carries field-level data.
- D3: `forgotPassword()` returns a discriminated result (register-style) — confirmed directly against `auth_password_reset.go` that it has a real, undocumented-in-spec `422` branch worth handling defensively.
- D4: A missing `token` on `/reset-password` and a `404` response render the **identical** message — matches `VerifyEmailStatus`'s existing R11 precedent and `patterns.md` §6's anti-enumeration convention.
- D5: Reset-password success is an **inline view + manual link to `/login`**, never an automatic redirect — matches `RegisterForm`/`VerifyEmailStatus`'s existing guest-facing terminal-success shape, not `useLogin`'s auto-`router.push`.
- D6: Every distinguishable failure branch on both forms (`422`/`404`/`410`/`429`) renders **frontend-owned Bahasa Indonesia copy**, never the backend's raw `detail`/`message` text — confirmed directly that every relevant backend string for these branches is an unlocalized English placeholder. A deliberate, evidence-based deviation from `RegisterForm`/`LoginForm`/`VerifyEmailStatus`'s existing verbatim-display pattern (flagged as a follow-up for those, not retrofitted here).
- D7: `ForgotPasswordForm`'s success view has no resend affordance — a second submission is already safe/independent per spec Assumption A.

**Top risks** (High-severity only — see §7 for the full table):
- A `422` on `/reset-password` accidentally routed through the terminal (`404`/`410`) branch — or a terminal outcome rendered as retryable — would violate spec Assumption B's explicit correctness requirement (a user must be able to fix a weak password and resubmit with the same link, never lose it to a validation mistake).

**Open items needing human input** — none open. All three items raised during drafting were resolved in this revision (copy strings decided, §4/§10; regen sequencing decided; backend follow-up scoped as a non-blocking backlog recommendation) — see §14 Resolved #6-#8.

## 1. Background

`docs/spec/1-account/features/04-forgot-reset-password.md` specifies `POST /auth/forgot-password` and `POST /auth/reset-password` (Tier 1 — INV-account-05/08). Both are already implemented and readable server-side (`backend/internal/domain/account/service.go:587-690`, `backend/internal/transport/http/auth_password_reset.go`) — confirmed directly during this synthesis, not assumed.

`page-map.md`'s Guest table lists `/forgot-password` ("Submit email to request password reset") and `/reset-password?token=...` ("Submit new password"), both Form-pattern pages. Neither exists as a real page today: `app/(auth)/forgot-password/page.tsx` and `app/(auth)/reset-password/page.tsx` are both 12-line placeholder stubs whose own header comment reads "Placeholder — real form is Account Task #4's scope ... Exists so the Auth Shell has a route to render against during this phase's verification." `login-form.tsx:151` already links to `/forgot-password`, and `login-form.test.tsx:44` already asserts that `href` — confirmed via the 1-explore logs, this half of the flow is done.

**Confirmed via direct backend/spec read during this synthesis (not visible from the frontend-only 1-explore logs) — three contract-drift findings, all material to this plan's design:**

1. **`lib/api/schema.d.ts` is stale.** `api/openapi/account.yaml:300-301` (and the already-regenerated bundle `api/openapi.yaml:330`) documents a `429` on `/auth/reset-password` — but the frontend's generated `schema.d.ts` (last regenerated before this addition) has no `429` in that endpoint's response union. The bundle itself is already correct; only the frontend-consumed generated file is behind.
2. **`/auth/forgot-password` has an undocumented `422` in the real backend.** `auth_password_reset.go:47-52` calls `WriteValidationError([{field:"email", message:"must be a valid email"}])` on a malformed email — `openapi/account.yaml` documents only `202`/`429` for this endpoint, and `schema.d.ts` matches that incomplete spec, not the real handler.
3. **`/auth/reset-password`'s `422` never carries field-level data, despite being documented as one.** `openapi/account.yaml:285-287` and the generated `schema.d.ts` type this branch as `components["responses"]["ValidationError"]` (a `ValidationProblem`, `Problem` + `errors[]`) — matching `register`'s shape. But `service.go`'s `validatePassword` (too-short OR breached password, lines 676-690) returns the bare sentinel `account.ErrValidation`, which `errors.go`'s `MapServiceError` (lines 76-81) maps to a **plain `Problem`** via `WriteProblem` — no `Errors` field at all, just a generic `detail: "The request was invalid."`. Building the originally-planned field-level `setError("new_password", ...)` mapping against this real response would silently do nothing (`body.errors` is `undefined`, the mapping loop iterates zero times) — no banner, no field error, nothing visible to the user after a weak-password submission.

A fourth, related finding shaped this plan's copy decisions (D6): the shared rate-limit middleware's `429` detail (`middleware.go:66`, `"Too many requests. Try again later."`) and every `Problem`/field `message` string touched by these two endpoints are unlocalized English, inconsistent with the rest of the app's Bahasa Indonesia UI — confirmed directly, not assumed, and true of `register`/`login`/`verify-email`'s already-shipped equivalents too (out of this task's scope to fix, see Open Item #3).

## 2. Scope

**In scope:**
- `ForgotPasswordForm` (`components/features/account/forgot-password-form.tsx` + `forgot-password-schema.ts`): email field, `202` generic success view (Banner + heading, focus-moved, link back to `/login`), defensive `422` field-error handling, `429`/generic-failure banners.
- `ResetPasswordForm` (`components/features/account/reset-password-form.tsx` + `reset-password-schema.ts`): `token` read via `useSearchParams()`, new-password field, terminal `404`/`410` states (form removed, link to `/forgot-password`), non-terminal `422`/`429`/generic-failure banners (form stays interactive, token untouched), inline `200` success view (link to `/login`).

- `lib/api/account.ts`: `forgotPassword()` (discriminated result, D3), `resetPassword()` (plain resolve/throw, D2).
- `lib/hooks/use-forgot-password.ts`, `use-reset-password.ts`: bare `useMutation` wrappers, no cache/redirect side-effect (neither endpoint issues a session).
- `lib/api/schema.d.ts`: regenerated (`npx openapi-typescript ../api/openapi.yaml -o lib/api/schema.d.ts` from `frontend/`, per `scaffold-frontend.md`'s documented command) — picks up the already-bundled `429` on `/auth/reset-password`.
- `mocks/handlers.ts`: default happy-path handlers for both endpoints.
- Component/unit tests (Vitest + React Testing Library + MSW) for every rule in §4.

**Out of scope (explicit):**
- Any backend change — the three drift findings in §1 are flagged for a human decision (Open Item #3), not fixed by this frontend-scoped task.
- Moving `/reset-password` out of the Auth Shell — considered and rejected, D1.
- A consolidated backend-copy/i18n pass across `/auth/*` Problem responses — flagged, not this task's to do unilaterally.
- Retrofitting `RegisterForm`/`LoginForm`/`VerifyEmailStatus` to stop showing backend `detail`/`message` verbatim — D6 applies only to this task's two new components; those three predate this discovery.
- Any other Account-domain page (MFA enrollment, account linking, profile, etc.).
- Any client-side replication of the backend's password-length/breach-list policy beyond UX-only length validation — per `frontend/AGENTS.md` §2, the breach check is server-only.

## 4. Rules & Validation

**`ForgotPasswordForm` / `forgotPassword()`**

- **R1** (idle state): Given `/forgot-password` loads, When rendered, Then it shows an email field, a submit button, and a "Kembali ke halaman login" link — no Google button/divider (unlike `/login`/`/register`, this is not an auth-provider flow).
- **R2** (client validation): Given the email field, When submitted empty or malformed, Then a client-side `zod` error ("Format email tidak valid") blocks submission before any request fires — UX only, per `form-validation-boundary.md`.
- **R3** (submit → `202`): Given any email (registered, unregistered, or Google-only — indistinguishable by design), When `POST /auth/forgot-password` returns `202`, Then swap to an inline success view: a focus-moved heading + `<Banner variant="success">` (the response's `message` if present — the backend's own `202` text is already correct Indonesian, `"Kalau email terdaftar, instruksi sudah dikirim."`, confirmed at `auth_password_reset.go:61`, so it's used verbatim rather than overridden by D6; that same string is also this component's `DEFAULT_SUCCESS_MESSAGE` fallback if `message` is ever absent) + a "Kembali ke halaman login" link. No resend affordance (D7).
- **R4** (submit → `422`, defensive — §1 finding #2): Given the backend rejects the email as malformed (a case client-side `zod` should already prevent in normal use), When `POST /auth/forgot-password` returns `422`, Then `setError("email", { message: "Format email tidak valid" })` — the same frontend-owned string as R2's `zod` message (D6), never the backend's literal `"must be a valid email"` — form stays visible, no banner.
- **R5** (submit → `429`): Given the shared per-IP rate limiter trips, When `POST /auth/forgot-password` returns `429`, Then render a frontend-owned `RATE_LIMITED_MESSAGE` banner — `"Terlalu banyak percobaan. Coba lagi beberapa saat lagi."` (D6, never the backend's confirmed-English `"Too many requests. Try again later."`), form stays visible.
- **R6** (submit → network/5xx/other): Then render the existing app-wide `GENERIC_ERROR_MESSAGE` banner, form stays visible.

**`ResetPasswordForm` / `resetPassword()`**

- **R7** (missing token): Given `/reset-password` loads with no `token` query param, Then render `<Banner variant="error">{INVALID_LINK_MESSAGE}</Banner>` — `"Link reset password tidak valid atau sudah digunakan."` — + a "Minta link baru" link to `/forgot-password` — no form rendered at all (D4, matches `VerifyEmailStatus`'s R11: a missing token is treated identically to a `404`).
- **R8** (idle state, token present): Given a `token` is present, When rendered, Then show a new-password field and a submit button.
- **R9** (client validation): Given the new-password field, When submitted with fewer than 8 characters, Then a client-side `zod` error blocks submission — length-only, UX only; the breach-list check is server-only and not replicated (matches `register-schema.ts`'s established comment/precedent).
- **R10** (submit → `200`): Given a valid token and a policy-passing password, When `POST /auth/reset-password` returns `200`, Then swap to an inline success view: `<Banner variant="success">` (the response's `message` — the backend's `200` text is already correct Indonesian, `"Password berhasil diubah. Silakan login ulang."`, confirmed at `auth_password_reset.go:95`, used verbatim and also as this component's default fallback, same reasoning as R3) + a "Masuk sekarang" link to `/login` — no automatic `router.push` (D5).
- **R11** (submit → `404`): Given the token doesn't exist or was already used, When `POST /auth/reset-password` returns `404`, Then a terminal state — form removed, `<Banner variant="error">{INVALID_LINK_MESSAGE}</Banner>` (the identical string as R7, D4) + link to `/forgot-password`. Never shows the backend's raw `detail` (confirmed English placeholder, D6).
- **R12** (submit → `410`): Given the token is expired, When `POST /auth/reset-password` returns `410`, Then a terminal state — form removed, `<Banner variant="error">{EXPIRED_LINK_MESSAGE}</Banner>` — `"Link reset password sudah kedaluwarsa. Silakan minta link baru."` — (frontend-owned, D6) + link to `/forgot-password`.
- **R13** (submit → `422` — confirmed no field data, §1 finding #3): Given the password fails the length policy or is breach-listed, When `POST /auth/reset-password` returns `422`, Then a **non-terminal** state — `<Banner variant="error">{WEAK_PASSWORD_MESSAGE}</Banner>` — `"Password tidak memenuhi syarat. Gunakan minimal 8 karakter dan hindari password yang umum digunakan atau pernah bocor."` — (frontend-owned, D6; never a field-level `setError`, since the real backend carries no field to map), form stays mounted and interactive, the `token` query param is untouched so the same link can be resubmitted (spec Assumption B — this is the correctness-critical branch, see §7's top risk).
- **R14** (submit → `429`): Non-terminal — same `RATE_LIMITED_MESSAGE` banner as R5 (`"Terlalu banyak percobaan. Coba lagi beberapa saat lagi."`), form stays interactive.
- **R15** (submit → network/5xx/other): Non-terminal — `GENERIC_ERROR_MESSAGE` banner, form stays interactive.

**Shared/infra**

- **R16** (mocks): `mocks/handlers.ts` gains default happy-path handlers — `POST /auth/forgot-password` → `202`, `POST /auth/reset-password` → `200`. Individual tests override every other branch via `server.use(...)`, matching the existing `register`/`login` convention.
- **R17** (schema regen): `lib/api/schema.d.ts` is regenerated (`npx openapi-typescript ../api/openapi.yaml -o lib/api/schema.d.ts`) before this task's `resetPassword()`/tests are written, so the `429` branch (§1 finding #1) is typed and testable like every other documented status.

## 5. Decision Log

**D1 — `/reset-password`'s shell placement**

| Option | Why rejected/accepted |
|---|---|
| A. Auth Shell, `app/(auth)/reset-password/page.tsx` rebuilt in place (**chosen, confirmed by Anhar 2026-08-26**) | `frontend/.agents/docs/phase0-shared-infra.md` Step 1 already lists this exact route under `(auth)` as a "resolved decision" from Phase 0 scaffolding — a specific, already-executed, named decision. Per this synthesis's Dedup & Reconciliation rule, a specific pre-existing decision outranks an analogy drawn from a different page's rationale. |
| B. Top-level route mirroring `/verify-email` (the 1-explore Stage 3 recommendation) | Rejected on revisiting — that recommendation was made without having read `phase0-shared-infra.md`'s Step 1 (not in the 1-explore reading list); it extended `/verify-email`'s Decision D1 reasoning (email-link entry, no prior navigation) by analogy, but a pre-existing, specific decision for this exact route takes precedence over a new analogy once found. The modal-blur-behind-`/` framing this option would have avoided is accepted instead as a known, low-severity trade-off (§7). |

**D2 — `resetPassword()`'s error-handling shape**

| Option | Why rejected/accepted |
|---|---|
| A. Discriminated result for `422` (`register`-style), `ApiError` throw for `404`/`410` (the original 1-explore Stage 3 hybrid design) | Rejected once confirmed directly against `service.go`: the real `422` response never carries `errors[]` — a discriminated "validation" branch would model data that doesn't exist. |
| B. Plain resolve-on-`200`/throw-`ApiError`-otherwise, matching `verifyEmail()`'s exact shape (**chosen**) | Matches the real backend contract directly: every non-`200` status (`404`/`410`/`422`/`429`/network/5xx) is handled identically at the API layer (thrown, caller branches on `.status`) — simpler than A, and doesn't imply field-level data that was never going to be there. |

**D3 — `forgotPassword()`'s error-handling shape**

| Option | Why rejected/accepted |
|---|---|
| A. Resolve-on-`202`-only, throw everything else (the original 1-explore Stage 2/3 design, closest to `resendVerification()`'s shape) | Rejected once confirmed directly against `auth_password_reset.go`: a real, undocumented `422` branch exists (malformed email) that deserves field-level handling, not a generic banner. |
| B. Discriminated result (`register`-style: `{ok:true}` / `{ok:false, kind:"validation", errors}`) (**chosen**) | Matches the real backend contract's actual branch count; defensive but cheap, and reuses an existing, already-tested shape (`register`'s) rather than inventing a third pattern. |

**D4 — Missing-token vs. `404` copy**

| Option | Why rejected/accepted |
|---|---|
| A. Distinct "malformed link" vs. "link no longer valid" messages | Rejected — a real, if narrow, enumeration signal (distinguishes "this link was never valid" from "this link was valid and got used/expired"), which `patterns.md` §6 and `VerifyEmailStatus`'s own R11 precedent both already guard against for the equivalent situation. |
| B. Identical message for both (**chosen**) | Matches the already-shipped precedent in this exact domain (`VerifyEmailStatus`'s R11) and the documented pattern convention — no new anti-enumeration reasoning needed, just consistency with what's already agreed. |

**D5 — Reset-password success: inline view vs. auto-redirect**

| Option | Why rejected/accepted |
|---|---|
| A. Automatic `router.push('/login')` on success, mirroring `useLogin`'s `onSuccess` | Rejected — `useLogin`'s redirect exists because that call *issues a session* the user is meant to land inside; `reset-password` issues no session (all sessions are revoked, the user must log in again) and every existing guest-facing terminal-success precedent in this domain (`RegisterForm`, `VerifyEmailStatus`) uses an inline view with a manual link instead, giving the user a moment to actually read "please log in again." |
| B. Inline success view (Banner + heading, focus-moved) + manual "Masuk sekarang" link (**chosen**) | Matches the two existing precedents directly; `useResetPassword` stays a bare `useMutation` with no side-effect, simpler than a bespoke redirect-on-success hook. |

**D6 — Error copy source: backend `detail`/`message` verbatim vs. frontend-owned copy**

| Option | Why rejected/accepted |
|---|---|
| A. Show backend `detail`/`message` verbatim, matching `RegisterForm`/`LoginForm`/`VerifyEmailStatus`'s existing precedent | Rejected for this task's two new components — confirmed directly (§1) that every relevant backend string for the branches these forms need to distinguish (`WriteValidationError`'s field messages, `MapServiceError`'s `Problem.detail`, the shared rate-limiter's detail) is unlocalized English, inconsistent with the rest of the app's Bahasa Indonesia UI. Reproducing the pattern here would ship visibly-wrong-language copy on brand-new code with no existing test/shipped behavior forcing consistency with it. |
| B. Frontend-owned Bahasa Indonesia copy per distinguishable branch, backend text never shown for `422`/`404`/`410`/`429` (**chosen**) | Internally consistent for both of this task's new components; sidesteps the localization gap cleanly without needing to change any backend code. Flagged as a deliberate deviation from `RegisterForm`/`LoginForm`/`VerifyEmailStatus`'s existing pattern — Open Item #3 recommends those get the same treatment in a later, consolidated pass, not silently forked further by this task. |

**D7 — `ForgotPasswordForm`'s success view: resend affordance or not**

| Option | Why rejected/accepted |
|---|---|
| A. Include a `ResendVerificationControl`-style resend affordance, mirroring `RegisterForm`'s success view | Rejected — there is nothing to "resend" against: spec Assumption A already establishes that a second `forgot-password` submission is independently safe (each token is guarded on its own single-use check), so a resend control would just be a second copy of the same form's own submit action with no distinct behavior. |
| B. Plain success view + link back to `/login` (**chosen**) | Simpler, and doesn't imply a dedup/resend mechanism that doesn't exist for this endpoint. |

## 6. Backward Compatibility

- **Database**: N/A — no persistence layer in `frontend/` (`frontend/AGENTS.md` §2). The backend's schema/migrations for this feature already shipped in the backend track, out of this plan's scope.
- **API**: No API changes from this plan — `POST /auth/forgot-password`/`POST /auth/reset-password` are already built, tested, and stable server-side (confirmed via direct code read, §1). The `schema.d.ts` regeneration (R17) is additive only: it adds a `429` key to an already-existing endpoint's response-status object type, which cannot break any existing caller (no key is removed or changed) — confirmed by inspecting the bundled `api/openapi.yaml`, which already has this branch documented; only the frontend's generated file was behind.
- **Existing clients/data**: `/forgot-password`/`/reset-password`'s current placeholder stubs are being replaced, not incrementally extended — both are self-labeled placeholders with no existing test file asserting their current (placeholder) content, so unlike `account/03`'s `/login` rewrite, there is no currently-passing test this plan directly contradicts. `login-form.tsx`'s existing `/forgot-password` link and its test (`login-form.test.tsx:44`) are unaffected — same href, no change needed.
- **Deprecation path**: N/A.
- **Runbook vs. Techplan check** (`rules.md` §3): no sub-component here has an independent operational lifecycle (no script, no cron, no separate rollback) — evaluated, doesn't apply. The `schema.d.ts` regen is a single mechanical command inside this same task, not a standalone runbook.

## 7. Edge Cases & Risks

**Business logic flow (concise, presentation-layer only — every branch is "what to render given what the backend already decided," never a re-derivation of a business rule):**
```

  submit -> POST /auth/forgot-password
    -> 202          => inline success view, no resend affordance (R3, D7)
    -> 422          => setError("email", frontend-owned copy) (R4, D6)
    -> 429          => banner, frontend-owned RATE_LIMITED_MESSAGE (R5, D6)

ResetPasswordForm (mounted on /reset-password inside the Auth Shell, wrapped in <Suspense>):
  token = useSearchParams().get("token")
  !token => terminal: banner INVALID_LINK_MESSAGE + link to /forgot-password, no form (R7, D4)
  else:
    render form (R8/R9)
    submit -> POST /auth/reset-password { token, new_password }
      -> 200        => inline success view, link to /login, no auto-redirect (R10, D5)
      -> 404        => terminal: banner INVALID_LINK_MESSAGE (same as R7) + link, form removed (R11, D4/D6)
      -> 410        => terminal: banner EXPIRED_LINK_MESSAGE + link, form removed (R12, D6)
      -> 422        => non-terminal: banner WEAK_PASSWORD_MESSAGE, form stays, token untouched (R13, D2/D6)
      -> 429        => non-terminal: banner RATE_LIMITED_MESSAGE (R14, D6)
      -> other      => non-terminal: banner GENERIC_ERROR_MESSAGE (R15)
```

## 9. Architecture / Plan

- Both forms follow `RegisterForm`'s established shape exactly: `react-hook-form` + `zodResolver`, a `<Banner variant="error">` as the form's first child for request-level failures (the Auth Shell's own documented convention), never attached to an input's own `error` prop for a request-level failure — the same structural guard `LoginForm` already relies on for the confirmed, not-fixed `/login` prototype Known Issue.
- `ResetPasswordForm` combines three shapes already established elsewhere in this domain: `LoginForm`'s banner-first-child convention, `VerifyEmailStatus`'s token-from-`useSearchParams()` + status-discriminated outcome convention (including its R11 missing-token precedent, D4), and `RegisterForm`'s idle/success-view toggle — but does **not** copy `VerifyEmailStatus`'s auto-fire-on-mount behavior, since a new password must be entered by the user first; the mutation only fires on submit.
- `resetPassword()`/`forgotPassword()` both go through the existing `postAccountAction` helper in `lib/api/account.ts` (never a raw `fetch`, per `api-client-centralization.md`), consistent with every other function in that file.
- No new TanStack Query *query* hook is needed — both are one-shot mutations (`useMutation`), consistent with `useRegister`/`useVerifyEmail`'s existing precedent. Neither writes to or invalidates any query cache: both endpoints are unauthenticated and issue no session, so there is nothing cached to update (matching `useRegister`'s own explicit "nothing is cached... so there's nothing this mutation needs to invalidate" reasoning).
- `app/(auth)/reset-password/page.tsx` wraps `<ResetPasswordForm />` in `<Suspense fallback={null}>` (D1) — the heading block renders outside the boundary since it doesn't depend on `useSearchParams()`, exactly mirroring `app/(auth)/login/page.tsx`'s existing `<Suspense fallback={null}>` around `GoogleCallbackError`. No new loading-fallback UI is needed (unlike the rejected top-level-route option, which would have needed its own fallback like `/verify-email`'s).
- `lib/api/schema.d.ts`'s regeneration (R17) is a standalone, mechanical first step — `resetPassword()`'s `429` handling and its tests depend on the regenerated types being in place first.
