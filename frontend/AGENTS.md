# AGENTS.md — frontend/

This file adds **Next.js/TypeScript-specific** conventions on top of
the root `AGENTS.md`. Read the root file first — the golden rules
there (no secrets/PII in logs, explicit authz assumptions, honest risk
reporting, scope discipline) apply here without repetition.

This file is scoped to `frontend/`. If you're working in `backend/`,
see `backend/AGENTS.md` instead.

## 1. Project layout

```
frontend/
├── app/                # Next.js App Router — routes, layouts, pages
├── components/         # shared UI components
├── lib/
│   └── api/            # types generated by openapi-typescript from ../api/openapi.yaml — do not hand-edit
└── public/
    └── manifest.json   # PWA manifest
```

- Route structure follows `docs/project/kencleng-frontend-tech-stack.md`
  and `docs/project/kencleng-ux-page-map.md` — the page map is the
  source of truth for which pages exist and what each persona can do
  on them, not an assumption made while implementing.

## 2. The frontend has no business logic

This is a hard boundary, not a style preference: `frontend/` is a
**pure presentation layer**. Validation shown to the user is a UX
convenience (immediate feedback via `zod` + `react-hook-form`); the
backend is the only source of truth for whether something is actually
valid. Concretely:

- Never compute or trust a total, balance, or eligibility check on the
  client and skip re-verifying it against what the API returns.
- Markdown rendering (e.g. `report_narrative`) must go through a
  library with built-in sanitization (`react-markdown` +
  `rehype-sanitize`) — never `dangerouslySetInnerHTML` on manually
  converted HTML. This is a presentation-layer security responsibility
  that belongs here, not in the backend.
- If a feature seems to need business logic in the frontend, stop and
  flag it — that's a sign the API contract is missing something, not
  a reason to add logic here.

## 3. State & data conventions

- **Zustand** for client-only UI/auth state (e.g. the in-memory access
  token) — not for server data.
- **TanStack Query** for anything that comes from the API — don't
  duplicate server state into Zustand.
- Types for API requests/responses come from `lib/api/` (generated).
  Don't hand-write a parallel type for something the OpenAPI schema
  already defines.
- Forms: `react-hook-form` + `zod` schema validation, matching the
  validation rules in the relevant `docs/spec/features/*.md` (not
  invented ad hoc).

## 4. Testing conventions

- Component/unit tests via `vitest`.
- Anything rendering user-controlled Markdown or HTML must have a test
  asserting a script/event-handler payload is stripped, not just that
  normal content renders correctly.
