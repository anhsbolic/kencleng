# AGENTS.md — frontend/

This file adds **Next.js/TypeScript-specific** conventions on top of
the root `AGENTS.md`. Read the root file first — the golden rules
there (no secrets/PII in logs, explicit authz assumptions, honest risk
reporting, scope discipline) apply here without repetition.

This file is scoped to `frontend/`. If you're working in `backend/`,
see `backend/AGENTS.md` instead.

## 1. Project layout

```
frontend/
├── app/                # Next.js App Router — routes, layouts, pages
├── components/
│   ├── ui/             # design-system primitives, no business awareness
│   ├── features/       # domain-specific components (e.g. features/donation/)
│   └── shared/         # cross-domain non-primitive components (e.g. MaskedField)
├── lib/
│   ├── api/            # fetch functions + types generated by openapi-typescript
│   │                    # from ../api/openapi.yaml — don't hand-edit the generated file
│   ├── hooks/           # TanStack Query hooks wrapping lib/api/
│   └── stores/           # Zustand stores, split per domain
├── mocks/                # MSW request handlers for tests
└── public/
    └── manifest.json     # PWA manifest
```

- Route structure follows `docs/project/kencleng-frontend-tech-stack.md`
  and `docs/ui-ux/page-map.md` — the page map is the source of truth
  for which pages exist and what each persona can do on them, not an
  assumption made while implementing. `docs/ui-ux/patterns.md` defines
  the reusable shape/state handling each page's pattern requires.

## 2. The frontend has no business logic

This is a hard boundary, not a style preference: `frontend/` is a
**pure presentation layer**. Validation shown to the user is a UX
convenience (immediate feedback via `zod` + `react-hook-form`); the
backend is the only source of truth for whether something is actually
valid. Concretely:

- Never compute or trust a total, balance, or eligibility check on the
  client and skip re-verifying it against what the API returns.
- Markdown rendering (e.g. `report_narrative`) must go through a
  library with built-in sanitization (`react-markdown` +
  `rehype-sanitize`) — never `dangerouslySetInnerHTML` on manually
  converted HTML. This is a presentation-layer security responsibility
  that belongs here, not in the backend.
- If a feature seems to need business logic in the frontend, stop and
  flag it — that's a sign the API contract is missing something, not
  a reason to add logic here.

## 3. State & data conventions

- **Zustand** for client-only UI/auth state (e.g. the in-memory access
  token) — not for server data.
- **TanStack Query** for anything that comes from the API — don't
  duplicate server state into Zustand.
- Types for API requests/responses come from `lib/api/` (generated).
  Don't hand-write a parallel type for something the OpenAPI schema
  already defines.
- Forms: `react-hook-form` + `zod` schema validation, matching the
  validation rules in the relevant `docs/spec/<domain>/features/*.md`
  (not invented ad hoc).

## 4. Testing conventions

- Component/unit tests via `vitest`.
- Anything rendering user-controlled Markdown or HTML must have a test
  asserting a script/event-handler payload is stripped, not just that
  normal content renders correctly.

## 6. One-off operational playbooks

For one-time setup work that isn't a feature (initial project scaffold,
and similar) — check `.agents/docs/README.md` for an index of available
playbooks before improvising the approach yourself. These are read on
demand, not loaded into every session's context — they cover things
that are relevant once, not on every task.

## 7. Related docs

- `docs/kencleng-agentic-workflow.md` — process, tiering, testing
  stages this file's conventions support.
- `docs/ui-ux/page-map.md` — page-by-persona source of truth.
- `docs/ui-ux/patterns.md` — reusable page-shape and state-handling
  definitions (loading/empty/error states, etc.) per pattern named in
  `page-map.md`. Wireframes are retired — this is the structural
  reference now.
- `docs/ui-ux/design-guidelines.md` — typography, color palette, and
  CSS custom properties. **Read this before writing any new component
  or page**, not just when something looks visually wrong — the
  project has already made these calls (Plus Jakarta Sans + Inter,
  green/amber/cool-gray palette), so there's no open decision here to
  make from scratch or default to something generic.
- `docs/ui-ux/prototype-reference.md` — tells you whether the page
  you're building has a Tier 1 prototype (near-final, build from it
  directly) or is Tier 2 (derive from `patterns.md` + nearest Tier 1
  precedent), and lists confirmed **Known Issues** in the prototypes
  that must NOT be carried into real implementation (e.g. the
  `/login` error state, the campaign card upload-placeholder bug).
  **Check this before treating anything in `design-reference/` as
  correct.**
- `docs/ui-ux/design-reference-usage.md` — how to extract and read
  `design-reference/`'s Claude Design exports (they're not plain
  HTML — see Step 1 there before trying to `cat`/grep a `.html` file
  directly), and what to take structurally vs. translate (inline
  `style={{var(--token)}}` → Tailwind classes) vs. ignore entirely
  (mock data, ad hoc `useState`, the reference's own scratch component
  library).
- `design-reference/` (repo root) — the actual prototype exports
  themselves. **Read-only, Tier 0 fenced — see root `AGENTS.md` §3.**
  Consult via the two docs above, never copy from it wholesale, never
  write to it.
- `docs/spec/<domain>/features/*.md` — acceptance criteria per
  feature/page, shared with the backend track (e.g.
  `docs/spec/5-donation/features/01-submit-donation-settlement.md`).
- Root `AGENTS.md` — golden rules, fencing, Definition of Done.

## 8. Output style

Default: terse. No filler, no hedging, no restating the question, no
sign-off. Applies to explanatory/conversational text only — never to
code, diffs, or configuration content.

Exception — full completeness required, do not compress:
- Any human-facing summary/digest section
- Any risk note
- Any PR description
- Any section explicitly governed by a self-check checklist in
  `../../harscode-workspace/workflow/` (e.g. techplan's Summary
  self-check, `workflow/2-techplan/rules.md` §7)

Source of this rule: `../../harscode-workspace/harness-optimization/
token-optimization.md` (the rule) and `.../claude-code/token-
optimization.md` (why this is enforced here rather than via a
third-party compression tool).
